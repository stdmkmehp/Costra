# 账本上下文（active family/ledger）刷新机制统一 —— 技术讨论与评估

> 状态：讨论稿（待团队评估实现方案）
> 日期：2026-07-06
> 涉及页面：明细页 `miniprogram/pages/ledger`、统计页 `miniprogram/pages/statistics`、协作页 `miniprogram/pages/family`
> 涉及服务：`miniprogram/services/family.ts`、`miniprogram/services/eventBus.ts`
> 相关组件：`miniprogram/components/ledger-switcher`（顶部账本切换器，本轮新增）

---

## 0. TL;DR

- **触发问题**：重命名账本后，协作页和明细页顶部账本名会更新，但**统计页顶部账本名不会即时更新**。
- **根因**：`setActiveFamily` 只在 `family_id/ledger_id` 变化时才广播 `ACTIVE_FAMILY_CHANGED`，重命名（仅 `ledger_name` 变）**不广播**；且各页的账本名更新其实主要依赖 `onShow` 重读 storage，而统计页 reShow 会短路、不重读。
- **延伸讨论**：能否让三个页面统一为「**首次 load context + 之后完全靠事件驱动**」的模式？
- **结论**：技术上可行，**统计页目前已经是这个模式的现成样板**；但要落地必须正视两个代价/前提（成员资格校验时机弱化、所有 context 变更路径都必须广播事件）。详见 §5、§6。

---

## 1. 背景

三个主 Tab 页（明细 / 统计 / 协作）顶部导航栏都展示「当前账本名」，并作为账本切换入口。本轮已将切换入口重构为公共组件 `<ledger-switcher>`（锚定下拉气泡，替代原生 `wx.showActionSheet`），切换动作收敛为：

```
组件选中账本 → switchActiveFamily() → setActiveFamily() 写 storage + 广播 ACTIVE_FAMILY_CHANGED → 三页 _onActiveFamilyChanged 响应重载
```

账本名的展示：三页都用 `<ledger-switcher name="{{ledgerName}}">`，`ledgerName` 来自各页自身的 `data`。

---

## 2. 问题描述

重命名账本（协作页 `onConfirmRenameFamily`）后：

| 页面 | 顶部账本名是否即时更新 | 
|---|---|
| 协作页（当前操作页） | ✅ 立即更新 |
| 明细页 | ✅ 切过去时更新 |
| 统计页 | ❌ 不更新（停留在旧名） |

---

## 3. 根因分析（基于代码事实）

### 3.1 重命名的写入路径

协作页 `onConfirmRenameFamily`（`family/index.ts` 1757+）：
1. 本页 `setData({ familyName })` —— **协作页顶部立即变**；
2. 调 `setActiveFamily(..., 'family-rename')` 把新 `ledger_name` 写进 storage。

后端 `updateFamily`（`server/src/services/familyService.ts` 333-350）确认：**`family.name` 与 `ledger.name` 同源同步**，返回 `name === ledger_name`。即事件里的 `ledger_name` 就是各页要显示的名字，无一致性风险。

### 3.2 `setActiveFamily` 的广播条件（关键根因）

```miniprogram/services/family.ts
  // 仅在 family_id 或 ledger_id 真正变化时广播，避免无意义刷新
  if (!prev || prev.family_id !== ctx.family_id || prev.ledger_id !== ctx.ledger_id) {
    ...
    eventBus.emit(EventNames.ACTIVE_FAMILY_CHANGED, payload);
  }
```

重命名时 `family_id / ledger_id` **都不变**（只有 `ledger_name` 变），所以**根本不广播事件**。
（注：`eventBus.ts` 的 `ActiveFamilyChangedPayload.source` 枚举里其实早已预留 `'family-rename'`，说明设计本应广播，属遗漏。）

### 3.3 各页账本名"更新"实际靠什么

重新核对三页的 `ACTIVE_FAMILY_CHANGED` handler，发现它们**都有 id 短路**，重命名时即使广播了也会 noop：

- 明细页（`ledger/index.ts` 436-441）：`if (this._ledgerId === p.ledger_id) return;` → 重命名 ledger_id 不变 → **return，不重载**。
- 统计页（`statistics/index.ts` 622-624）：`if (this._familyId === … && this._ledgerId === …) return;` → 同样 **noop**。

那明细页为什么"切过去名字就对了"？——因为**明细页 `onShow` 每次都无条件跑 `_loadContext`**（`ledger/index.ts` 462-487，无短路），`_loadContext` 里 `getActiveLedgerName()` 从 storage 重读了新名并 `setData`。

而**统计页 `onShow` 在 reShow 时走 `_initialized` 短路**（`statistics/index.ts` 217-227），**不跑 `_loadContext`**，所以读不到新名字。

> **一句话根因**：重命名只写了 storage、没广播事件；账本名的更新又主要依赖 `onShow` 重读 storage，而统计页 reShow 会短路不重读，于是统计页不更新。

## 4. 三页现状对比（事实）

### 4.1 `onShow` 数据刷新策略

| 页面 | onShow 行为 | 是否每次重读 context |
|---|---|---|
| 明细页 | 每次都 `await _loadContext(); await _loadEntries();`（`_loadEntries` 内建"热刷新静默重载" `_reloadCurrentMonthSilently`，签名 diff、无变化一帧不动） | **是**（每次） |
| 统计页 | 首次：`_initialized=true` + `_loadContext + _loadData`；reShow：**短路**，仅 measure pane（除非有 pending action） | **否**（仅首次 + 事件） |
| 协作页 | 每次 `_loadPage({ preserveExistingView })`（有 SWR 缓存快路径 + 不闪 loading） | 是（每次，带 preserve 优化） |

### 4.2 事件订阅（均 onLoad 注册 / onUnload 注销）

| 事件 | 明细页 | 统计页 | 协作页 |
|---|---|---|---|
| `ACTIVE_FAMILY_CHANGED` | ✅（id 短路→`_onActiveFamilyChanged`→`_loadContext+_loadEntries`） | ✅（id 短路→`_loadContext+_loadData`） | ✅（family_id 短路→`_loadPage`） |
| `SYNC_DONE`（pulled>0） | ✅ `_refreshIfChanged`（只重载 entries） | ✅ `_onSyncDone` | ✅ |
| `ENTRY_SAVED` / `ENTRY_UPDATED` | ✅ `_loadEntries` | ✅ `_onSyncDone` | ✅ |
| `CATEGORIES_LOADED` | ✅ 重渲 | — | — |
| `PROFILE_UPDATED` | ✅ 更新自身头像 | ✅ 更新 memberTabs | ✅ 更新 members |

> 重要事实：Tab 页 `onUnload` 只在页面销毁时触发，而 Tab 页在后台通常**不销毁**，所以**后台 Tab 页始终保持订阅、能收到事件**。这是"后台页也能靠事件更新"成立的前提。

### 4.3 `_loadContext` 到底做了什么（不止读账本名）

明细页 `_loadContext`（`ledger/index.ts` 559-626）：
1. 并行读 `getActiveLedgerId / getActiveFamilyId / getActiveFamilyKind / getActiveLedgerName`，确定 `_ledgerId / _familyId`（**`_loadEntries` 强依赖**）；
2. `showMemberFilter` 成员筛选入口可见性；
3. **`_validateFamilyMembership`：协作账本成员资格后台校验**（被踢出 → `fallbackToPersonalFamily` 回退个人账本 + toast）；
4. `_loadMemberMap`（列表行头像）；
5. `getCategories` 分类预热；
6. 非共享账本重置筛选。

统计页 `_loadContext`（`statistics/index.ts` 306-360）：**同样包含成员资格校验**：
```318:337:miniprogram/pages/statistics/index.ts
    if (familyKind === 'shared' && familyId) {
      try {
        const { families } = await getFamilies();
        const matched = families.find((f) => f.id === familyId && f.ledger_id === ledgerId);
        if (!matched) {
          const fallback = await fallbackToPersonalFamily('ledger-switch');
          ...
          wx.showToast({ title: '你已不在该账本中', icon: 'none' });
```
外加 `getFamilyMembers` 构建 `memberTabs`。

## 5. 提议方案：三页统一为「首次 load + 纯事件驱动」

**核心思路**：`onShow` 不再每次重读 context；页面只在**首次**初始化时 load 一次 context，之后**完全靠事件**驱动更新：
- `ACTIVE_FAMILY_CHANGED` → 重建 context / 数据（覆盖"切换账本""重命名账本"）；
- `SYNC_DONE / ENTRY_SAVED / ENTRY_UPDATED` → 刷新数据；
- `PROFILE_UPDATED / CATEGORIES_LOADED` → 局部刷新。

**可行性论证（事实支撑）**：
- **统计页已经是这个模式的活样板**（首次 `_loadContext`，reShow 短路，靠事件）。说明该模式在本项目已验证可行。
- 后台 Tab 页保持事件订阅（§4.2），能接收事件，因此"后台页也能被事件更新"成立。
- 数据刷新层面，`SYNC_DONE / ENTRY_*` 已覆盖记账/编辑/同步导致的数据变化；`triggerOnPageShow` 触发的 sync 也会经 `SYNC_DONE` 回流。

若落地，明细页 `onShow` 的 `_loadContext + _loadEntries` 可像统计页那样收敛为"首次 + 事件"，三页对齐。

---

## 6. 必须正视的两个代价 / 前提（不是免费的）

### 代价 1：成员资格校验（被踢出 → 回退）的时机会弱化

这是明细页与统计页目前**唯一实质性行为差异**：
- 明细页：每次 `onShow` 都 `_loadContext` → **每次切回来都校验"我是否还在这个账本"**（`_validateFamilyMembership`）。
- 统计页：reShow 短路 → **不校验**，只在首次 + 切账本事件时校验。

事实核查：被踢出账本**没有任何事件**通知本端；`triggerOnPageShow` 触发的 sync 走 `SYNC_DONE → _refreshIfChanged`，只重载 entries、**不重新校验 context / 成员**。

因此若明细页改为"首次 + 纯事件"，**会丢掉"每次切回来即时检测被踢出"的能力**，退化为"下次主动切账本 / app 重启才回退"。统计页已接受这个弱化，但明细页是首屏、协作场景更敏感，需产品确认可接受性。

**两种处理选项（待评估）**：
- **选项 A（接受弱化）**：向统计页看齐，接受被踢出检测延迟。改动小、三页彻底一致。
- **选项 B（补齐事件，真正纯事件）**：把"成员 / 资格变化"也事件化（例如后端下发变更、或并入 sync 流程产出一个"成员变更"事件），让被踢出 / 成员增减也能事件驱动。改动大但语义完整，不牺牲即时性。

### 代价 2：所有会改变 context 的路径都必须广播 `ACTIVE_FAMILY_CHANGED`

"首次之后完全靠事件"成立的前提是：**任何 context 变化都广播事件**。而现状 `setActiveFamily` 只在 `family_id/ledger_id` 变化时 emit —— **重命名（仅 `ledger_name` 变）不 emit**（即 §3.2 的 bug 根源）。

因此走纯事件路线，**至少要先补齐**：
1. `setActiveFamily` 广播条件加入 `ledger_name` 变化（让重命名也 emit，`source='family-rename'`）；
2. 各页 `ACTIVE_FAMILY_CHANGED` handler 的 **id 短路逻辑需要调整**——当前"id 不变即 return"会把"仅改名"事件挡掉（§3.3）。需要区分"切换账本（重建数据）"与"仅改名（只更账本名）"两种响应；
3. 未来任何新增的 context 变更路径都必须保证 emit。

> 补充：账本名这一层，另一种更内聚的做法是让 `<ledger-switcher>` 组件**自身**订阅 `ACTIVE_FAMILY_CHANGED`、用 `payload.ledger_name` 自更新显示名（组件已是三页共用），这样"改名即时同步"不必依赖各页 handler，天然覆盖后台常驻的统计页。此法可与代价 2 的 (1) 配合，规避 (2) 中对各页 handler 的改动。

## 7. 待团队评估的问题

1. **代价 1 的取舍**：选 A（接受被踢出检测弱化）还是 B（新增成员 / 资格变更事件）？这决定"纯事件"是否语义完整。
2. **账本名同步的落点**：放在 `<ledger-switcher>` 组件自订阅（内聚、覆盖后台页），还是继续放在各页 handler（需改 id 短路逻辑）？
3. **onShow 重载是否真要全部去掉**：明细页 `_loadEntries` 已有静默重载优化，"每次 onShow 重载"的视觉/性能成本其实很低；去掉它换来的收益（一致性）是否值得丢掉兜底刷新？（统计页去掉是因为其 DOM 重建成本高、会打断滚动 / 展开态；明细、协作页情况不同。）
4. **协作页**：`_loadPage` 每次 onShow 执行，是否也纳入"首次 + 事件"，还是维持 SWR + preserve 现状？
