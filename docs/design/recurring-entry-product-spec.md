## 1. 背景与问题

### 1.1 用户痛点
| 场景 | 用户实际行为 | 现在的问题 |
|---|---|---|
| 每月房租 8000（固定日 · 固定金额） | 每月手动记一笔 | 忘记记 → 月度统计失真 |
| 每月工资 20000（固定日 · 固定金额） | 发薪日记一笔 | 忘记 → 收入被低估、预算失真 |
| 每周固定家政 200 | 记不清有没有记过 | 重复记 or 漏记 |
| 每年 12 月房屋保险 2400 | 一年一次几乎必忘 | 全年账不完整 |
| iCloud 6 / 视频会员 25 / … 多个订阅 | 分散在不同日期 | 手动维护成本高，很多用户干脆放弃 |

共同特征：**金额、分类、账户、备注在下一次发生时几乎不变**。用户真正需要的是一个"设一次、之后自动帮我记"的能力。

### 1.2 与 COSTRA-302 的关系
COSTRA-302 原描述里包含"cron + 订阅消息提醒"两部分。本方案**只做前者**（自动生成流水），**不做后者**（订阅消息提醒），理由见 §2.1。COSTRA-302 中关于订阅消息的 AC-2/3/4 视为本期不落地部分，未来是否补做由运营数据回看再定。

## 2. 产品目标与非目标

### 2.1 目标（本期做）
1. 让用户能把"每月房租/每月工资/每周家政/每年保险/月订阅"这类**规律性收支**一次设定、长期跑。
2. 到期后**在后台静默自动落账**，无提醒、无待确认队列、无需用户任何介入。
3. 定时记账**归属于用户**，不绑定账本 —— 单人用户 / 协作账本 owner / 协作账本成员都能设定，跟随人走；同一用户切换账本、加入 / 退出家庭对已有的定时规则**尽可能不产生副作用**（边界见 §7）。
4. 用户能在一个入口（mine 页）看到自己所有定时规则，能新增 / 修改 / 复制 / 启用 / 禁用 / 删除。
5. 生成的流水**在明细页可视化可识别**（形式待评估，见 §6），但不影响任何统计口径。

### 2.2 非目标（本期明确不做）
- **推送 / 订阅消息提醒 / 待确认队列**：完全不做。到时间就直接自动记入，避免打扰。
- **动态金额 / 智能建议**：本期金额、分类、备注 100% 用用户设定值。
- **复杂 cron 表达式**（如"每月最后一个工作日" / "工作日"）：只支持 §4 定义的档位。
- **多币种 / 汇率换算**：完全沿用 entries 现有单币种约束。
- **导入其它 App 的定时账单**：不做。
- **上线运营指标 / 度量目标**：本期只关注功能正确，不做数据目标（用户明确要求）。

## 3. 归属模型（关键决策）

**定时规则跟随「人」而非「账本」。**

| 维度 | 决策 |
|---|---|
| 谁能设定 | 单人用户 / 协作账本 owner / 协作账本 member，**所有登录用户均可** |
| 数据归属 | `recurring_rules.created_by = user_id`，规则本身与用户一一挂靠 |
| 账本字段 | 规则里**记录一个目标 ledger_id**（用户在设定时选的账本），执行时把 entry 记到这个账本上 |
| 可见性 | 每个用户在 mine → 定时记账里，**只看到自己创建的规则**；协作账本其他成员看不到你的定时规则列表 |
| 谁能改 / 删 | 只有 `created_by` 本人（含 owner 都无法改他人的定时） |
| 执行时的身份 | 自动生成的 entry 的 `created_by` = 规则的 `created_by`；不会因为规则被自动执行而变成"系统用户" |
| 账本无效边界 | 目标账本被删 / 用户被移出该协作家庭 → 规则**自动禁用**（不再执行），列表页红字提示（详见 §7） |

> 这一决策来自用户明确要求，**推翻了 v0.1 里"定时归账本"的默认思路**。技术方案需要相应修订：`recurring_rules` 表按 `created_by` 索引查询，而不是按 `ledger_id`。

## 4. 周期规则（v0.3 修订）

### 4.1 支持六档周期
| 档位 | 用户配置内容 | 多选上限 | 举例 |
|---|---|:---:|---|
| **每周** | 选择一周中的若干天（周一~周日） | 7 | 每周一、三、五 |
| **每两周** | 选择一周中的若干天，以起始日所在周为 W0，W0/W2/W4 触发 | 7 | 每两周的周三、周日 |
| **每月** | 选择该月中的若干天（1~31） | 7 | 每月 5 日、15 日、25 日 |
| **每两月** | 选择该月中的若干天，从起始月起隔月触发 | 7 | 每两月的 1 日、15 日 |
| **每三月** | 选择该月中的若干天，从起始月起每三个月触发一次 | 7 | 每三月的 1 日 |
| **每年** | 先选一个月，再在该月里选若干天 | 7 | 每年 12 月的 24 日、25 日、31 日 |

> ⚠️ 与 v0.2 的差异：
> - **新增每两月 / 每三月两档**（用户明确要求）
> - **每月 / 每两月 / 每三月 / 每年**从 v0.2 的"单选一天"改为**多选（最多 7 天）**
> - 每年由"选月 + 选日"的组合变为"先选一个月 → 在该月里选最多 7 天"，与月度选择器复用同一控件

### 4.2 多选的通用语义
- 所有支持多选的档位，**每一个被选中的日子都是一次独立的执行**，各自幂等，互不影响。
- 举例 1："每周一、三、五 · 200 元 · 打车" → 每周会自动生成 3 条流水，`occurred_at` 分别落在周一、三、五。
- 举例 2："每年 12 月 24、25 日 · 500 元 · 礼物" → 每年 12 月产生 2 条流水。
- 举例 3（跨月）："每年 1 月 1 日、2 月 2 日、… 12 月 12 日 各一笔" → 每年产生 12 条流水，分别落在这 12 个日子。
- 未选任何天时表单不可保存。
- **每档的多选上限（差异化）**：
  | 档位 | 上限 | 理由 |
  |---|---|---|
  | 每周 / 每两周 | **7 天** | 一周只有 7 天，物理上限 |
  | 每月 / 每两月 / 每三月 | **14 天** | 支持"半月双周"等更密的场景 |
  | 每年 | **12 天** | 支持"每月 1 号各记一笔"这类年度全月覆盖场景 |
- 若用户已勾满上限，第 N+1 个 tap 会有轻震动提示 + toast "最多可选 X 天，先取消一个再选"（X 随档位取值）。

### 4.3 "每 N 周期"的基准周 / 基准月
- **每两周**：`start_date` 所在的自然周为 W0（周一开始）；W0 / W2 / W4 … 触发
- **每两月**：`start_date` 所在的自然月为 M0；M0 / M2 / M4 … 触发
- **每三月**：`start_date` 所在的自然月为 M0；M0 / M3 / M6 … 触发
- 暂停/禁用后恢复：基准不变，从恢复时刻之后的下一个匹配日起算，**不补跑期间漏掉的次数**。

### 4.4 边界规则
| 情况 | 规则 | 举例 |
|---|---|---|
| 每月 / 每两月 / 每三月 勾选了 31 日，但当次周期只有 30 天 | 该日**回落到当月最后一天**，其它被勾选的日子照常触发 | 每月 15 日 + 31 日 → 4 月生成 4/15 + 4/30 两条 |
| 每月 勾选了 29/30/31 日，当次周期是 2 月 | 平年落 2/28；闰年 29 落 2/29、30/31 均落 2/28 | — |
| 每年 · 2 月 · 勾选 29 日 | 平年落 2/28，闰年落 2/29 | — |
| 起始日 = 今天且今日恰好是被勾中的日 | 若"今日的执行时段"仍未过 → 今天就会触发一次；若已过 → 等下一个匹配日 | 今天 07:00 设"每周一 · 早上"，今日周一 → 早上时段还有 → 今天上午会触发 |
| 起始日在未来 | 从起始日起算 | 7/20 设起始 8/1，下次 8/1 |
| 用户设的多选日子当次周期一个都没有匹配上 | 该周期空跑，直接推进到下一周期 | 每三月的 31 日，2/4/8/10 月都会各自回落到月末，不会空跑 |
| 结束日到期 | `next_run_at > end_date + 23:59:59` 时规则置 `ended`，不再执行 | — |
| 服务器错过某次执行时间 ≤ 24h | 恢复后**为该次周期补 1 条**（同一"周期日"的多个应生成条目只补 1 条），> 24h 不补 | — |

### 4.5 每次执行的"具体时段"
用户选择**四档模糊时段**，具体分钟由后台错峰分配：

| 用户看到的选项 | 后台落地窗口（用户本地时区） |
|---|---|
| 凌晨 | 00:00 ~ 05:59 |
| 早上 | 06:00 ~ 11:59 |
| 下午 | 12:00 ~ 17:59 |
| 晚上 | 18:00 ~ 23:59 |

- 后台在用户创建规则时，为其**用 `hash(user_id + rule_id) mod 窗口分钟数`** 计算出一个稳定的具体分钟并落库。此后每次执行都用同一时点，避免"这个月凌晨 1 点、下个月凌晨 5 点"的漂移感。
- 同一规则里如果有多个被勾中的日子（例如每周一、三、五），三次执行的**分钟点相同**（哈希输入不带日子），用户能形成"我的定时就是凌晨 3 点 12 分"的稳定预期。
- 时区快照到规则；`users.timezone` 变更不主动改规则时区。
- 用户切换时段（例如凌晨改早上）→ 用新窗口重新计算分钟并覆盖持久化。

## 5. 交互设计

### 5.0 视觉与色板约定（本节所有页面必须遵守）

> 依据 `design/ui/design_spec.md` §2 基调 + 用户在 v0.3.2 明确"色板采用莫兰迪，不强求微信绿"。

**基调（硬约束 · 遵守 design_spec）**：
- 页面底色：**暖灰白** `#f1f2ec`
- 主文字：**油墨暖黑** `#1c1b1a`
- 副文字：`rgba(28,27,26,0.48)`
- 极弱文字（占位/禁用）：`rgba(28,27,26,0.28)`
- 分组卡片：纯白 `#ffffff` + 圆角 `24rpx` + **无阴影**（Inset Grouped 风格，与 mine 页对齐）
- 卡片间距：**32rpx**；卡片内条目间距：**24rpx** 上下 padding
- **绝对禁止**：分割线滥用、卡通插画、深阴影、彩色渐变、多色饼图

**莫兰迪功能色板（本功能专用）**：
| 用途 | 色号 | 说明 |
|---|---|---|
| **选中态 / 强调**（CTA、tag 选中、开关开启） | `#8AA98F` | 莫兰迪苔绿 · 编辑页周期 tag 选中、保存按钮、"已启用"开关 |
| **警示 / 上限**（tag 拒绝、失败状态） | `#C08A7B` | 莫兰迪陶土红 · 上限拦截时的一次性 tag 抖动色、账本失效红字 |
| **提醒 / 待办**（禁用规则红字、需注意） | `#C2A56A` | 莫兰迪琥珀 · "已禁用" tag 副标签、"分类已降级"顶部黄条 |
| **信息 / 弱提示**（顺延说明、辅助文字） | `#A0A69C` | 莫兰迪灰绿 · 底部辅助提示、"预计下次执行" 前的图标色 |
| **"公"字角标**（现状保留） | `#6B9B8F` | 现有石青，不动 |
| **"定"字角标** | `#A88A5E` | 莫兰迪砂棕，v0.3 定稿 |

**动效基准**：
- 常规过渡：`200ms cubic-bezier(0.4, 0, 0.2, 1)`（快速反馈）
- 状态摘要条数值变化：`160ms ease-out`
- 面板/action-sheet 展开：`280ms ease-out`（与 design_spec §6.2 过滤面板一致）
- 上限拦截 tag 抖动：`180ms · X 轴 ±8rpx · 3 帧`

**震动分级**：
- 上限拦截：`wx.vibrateShort({ type: 'light' })`
- 保存成功：`wx.vibrateShort({ type: 'medium' })`（一次性反馈）
- 删除确认后：不震动（避免与二次确认弹窗动效冲突）

**tag / 控件的统一形态**：
- 未选态：白底 `#ffffff` · 1rpx 边框 `rgba(28,27,26,0.12)` · 主文字 `#1c1b1a`（不是灰字，保证可读性）
- 选中态：**填充 `#8AA98F` 苔绿** + 白字 `#ffffff` + 无边框
- 禁用态（超上限时保持可点，但已选态优先）：不再单独灰化，通过震动 + toast 拒绝
- **点击反馈**：tag 按下瞬间 `transform: scale(0.94)`，`120ms ease-out` 回弹

- 当前月份 tab = 2 月 且 已勾 2/29 → 显示 `ⓘ 勾中 2/29 时，平年会顺延到 2/28`
- 当前月份 tab = 其它月 且 已勾 29/30/31 → 显示 `ⓘ 勾中 29/30/31 时，当月无该日会顺延到当月最后一天`（同 c）

**为什么放弃"单选月份 + 交集保留"的原设计**：
- 旧设计假设"一个规则只覆盖一个月"，无法表达跨月场景（1/1、2/2、… 12/12）
- 新设计核心洞察：**月份 tab 从"选一个"降级为"翻页"，选择状态挂在 `(月, 日)` 组合上**；上限从"每月独立"变为"全局 12 天共享"，语义更直白

**校验**：
- 单个月内允许 0~上限（受总额 12 约束）天被勾中
- 总天数 ≥ 1 才能保存

**卡片视觉**：

**主行**（自然语言描述）：
- 左侧 `⟳` 循环图标 · 色 `#A0A69C` 灰绿 · 尺寸 `36rpx`

**自然语言模板（编辑页预览 · 完整明确列出）**：
| 周期档位 | 描述模板 | 举例 |
|---|---|---|
| 每周 | `每周 <dow列表> · <时段> · <账本名>` | 每周一、三、五 · 下午 · 我的家庭 |
| 每两周 | `每两周 <dow列表> · <时段> · <账本名>` | 每两周的周日 · 早上 · 我的家庭 |
| 每月 | `每月 <dom列表> 日 · <时段> · <账本名>` | 每月 5、15、25 日 · 凌晨 · 我的账本 |

**列表格式化子规则（编辑页 · 完整明确）**：
- **dow**：按周一→周日语序合并。`一、二、三` → `周一、二、三`；`一~日` 全选 → `每天`
- **dom（每月类）**：升序排列，连续 3 个及以上用 `~`（`5、6、7、8` → `5~8`），非连续用中文顿号 `5、10、15`
- **(月, 日) 每年**：
  - 按月排序 → 月内按日排序
  - 同月多天合并 `M 月 D1、D2 日`（连续 3+ 天用 `~`：`3 月 1~3 日`）
  - 不同月用中文顿号 `1 月 1 日、2 月 14 日`
  - **编辑页无特殊简化模板**（用户明确要求"编辑页必须让用户明确知道选了哪些天"）

**列表格式化子规则（非编辑场景 · 列表页副行 / 未来其它摘要位置）**：
- 已选 ≤ 3 天：完整展示
- 已选 ≥ 4 天：**保留首 2 尾 2，中间省略号**
  - 每周：`周一、二、…、六、日`
  - 每月：`5、10、…、25、31 日`
  - 每年：`1/1、2/2、…、11/11、12/12`
- 由 `formatDaysForSummary(days, mode: 'full' | 'compact')` 单一工具函数产出，编辑页传 `full`，列表页传 `compact`

**下次执行时间的计算**：由前端 `computeNextRunAt(rule, now)` 纯函数产出（与后端同源，共享同一份算法定义 · 见技术方案）。用户还未选够日子时该块显示占位 `—`。

### 5.4 交互反馈总览（编辑页 · 列表页共用）

为了让"关键信息要素有良好的可视效果"，本节把各类反馈按**优先级**和**打断度**统一编排，避免动效泛滥。

#### 5.4.1 反馈分级

| 级别 | 触发场景 | 反馈形式 |
|---|---|---|
| **P0 破坏性操作** | 删除规则 · 清空所有已选 · 放弃编辑 | `wx.showModal` 二次确认 · 主按钮陶土红 `#C08A7B` |
| **P1 有效操作** | 保存成功 · 启用/禁用规则 · 复制规则 | 顶部 toast + 中震动一次 |
| **P2 系统拒绝** | 上限拦截 · 校验未通过 | 目标元素抖动 + 陶土红闪 + 轻震动 + toast |
| **P3 状态更新** | 计数从 3 变 4 · 摘要条列表刷新 · 预览时间更新 | 数值 `160ms ease-out` 淡入 · 无震动 · 无 toast |
| **P4 无声更新** | 卡片折叠 / 展开 · 分组重排 | `200ms ease` 平滑动效 · 无提示 |

#### 5.4.2 动效时长表

| 场景 | 时长 | 缓动 |
|---|---|---|
| tag 按下反馈 | `120ms` | `ease-out` scale(0.92) → 1.0 |
| 状态摘要条数值刷新 | `160ms` | `ease-out` 淡入 |
| 段控件下划线滑动 | `200ms` | `ease-out` |
| 卡片内数值/文本切换 | `200ms` | `cubic-bezier(0.4, 0, 0.2, 1)` |
| 上限拦截抖动 | `180ms` | `linear · 3 帧` |
| 陶土红 flash | `120ms` | `ease-out` 淡入淡出 |
| Action-sheet 展开/收起 | `280ms` | `ease-out` |
| 保存后自动返回 | `280ms` | `ease-out` 淡出 |

#### 5.4.3 关键信息的可视权重（本方案的视觉重心排布）

从上到下按视觉权重排列（用于设计稿评审时对齐）：

1. **最强**：保存按钮通过态（苔绿加粗，右上常驻）
2. **次强**：预览卡片的"下次执行日期"（44rpx 主文字 + 等宽数字）
3. **中强**：摘要条的已选天数 `N` 数值（≥1 时苔绿加粗） · 每年月份 tab 的上标徽标（苔绿圆点白数字）
4. **中**：已选 tag（苔绿填充白字）· type tab 选中态（白底黑字 + 苔绿下划线）
5. **弱**：卡片内其余 value（主文字色但字重 400）· 顶部 toast
6. **最弱**：辅助提示（灰绿字号 22）· 副行文字（rgba 0.48）

> 该权重排布确保用户第一眼看到的是"保存 + 下次执行时间"，第二眼扫到"已选了几天 · 每月哪些天参与"，最后才是控件本身。

#### 5.4.4 无障碍与容错

- 所有 tag、行、按钮的 `aria-label`（微信 `aria-label` 无障碍属性）都补齐语义：`已选周一` · `未选 5 号，点击选择` · `已选 3 天中的第 1 天` 等
- 网络请求失败：保存失败 toast + 按钮回到可点态；不清除用户已填入的表单值
- 编辑页初次进入若上下文缺失（如无 active ledger）：账本行显示占位 `请选择账本` 陶土红，并高亮该卡片外框，引导用户填入

## 6. 明细页的可视化标识（v0.3 定稿）

采用**"定"字角标**方案，与"公"字角标形成一组姊妹标识：

### 6.1 显示规则（四种流水状态）

| 流水状态 | 头像/图标右下角显示 |
|---|---|
| 非公 · 非定时 | 无 |
| **公** · 非定时 | 单个"公"字（现状） |
| 非公 · **定** | 单个"定"字 |
| **公** · **定** | 两字并排：**"定 公"**（定在左、公在右） |

并排时**两字水平相邻、垂直中线对齐、共享同一 padding 逻辑**，视觉上像一个"复合小标"，不额外撑出气泡背景。

### 6.2 "定"字视觉规范（严格对齐"公"字）

参照现有 `.entry-member__badge` / `.entry-member__badge-text`：

```wxss

.entry-member__badge-recurring {
  font-size: 18rpx;
  line-height: 1;
  font-weight: 800;
  color: #A88A5E;                    /* 莫兰迪·砂棕（下详） */
  text-shadow:
    1rpx 0 0 var(--color-role-bg-app, #f1f2ec),
    -1rpx 0 0 var(--color-role-bg-app, #f1f2ec),
    0 1rpx 0 var(--color-role-bg-app, #f1f2ec),
    0 -1rpx 0 var(--color-role-bg-app, #f1f2ec),
    1rpx 1rpx 0 var(--color-role-bg-app, #f1f2ec),
    -1rpx -1rpx 0 var(--color-role-bg-app, #f1f2ec),
    1rpx -1rpx 0 var(--color-role-bg-app, #f1f2ec),
    -1rpx 1rpx 0 var(--color-role-bg-app, #f1f2ec);
}
```

**字号、粗细、投影**与"公"字**完全一致**，仅颜色不同。

### 6.3 "定"字颜色选择（莫兰迪 · 砂棕 `#A88A5E`）

选色原则：
1. 与"公"字（`#6B9B8F` 石青）**色相相反**：石青位于 HSL 色轮 165° 附近，取其对角 345° 附近的暖色系，视觉上一冷一暖、一"公"一"定"，语义联结强
2. 与米白底 `#f1f2ec` 有足够对比度（`#A88A5E` 在浅色底上 WCAG AA 通过）
3. 与 `MEMBER_COLOR_SLOTS`（成员配色）**无重叠**：`E0A074`（暖橘）、`C2A878`（赭石）、`CCA98F`（茶褐）都是暖色但更饱和；`#A88A5E` 更沉稳、饱和度更低（HSL S ≈ 30%），不会被误认为成员色
4. 保持莫兰迪美学（低饱和、中等明度）

**候选池**（供你在评审时快速换色）：
| 色号 | 名字 | 说明 |
|---|---|---|
| `#A88A5E`（**推荐**） | 砂棕 | 温暖沉稳，与石青对角互补 |
| `#B69B6F` | 卡其 | 更亮一点，用于米白底可能对比不够 |
| `#9E7F55` | 深砂 | 更暗一点，与石青同明度 |
| `#B08968` | 铜棕 | 偏红一些，暖感更强 |

**默认采用 `#A88A5E`**。若真机上视觉稿对比后觉得偏暗，回退到 `#B69B6F`。

### 6.4 "定 公"并排的实现约束

- 现有 `.entry-member__badge` 是绝对定位在头像右下（`right: -6rpx; bottom: -6rpx`），且只承载一个字
- 并排需要把 badge 从"单字"改造为"字容器"：
  ```wxml
  <view wx:if="{{entry.isRecurring || entry.isShared}}" class="entry-member__badge">
    <text wx:if="{{entry.isRecurring}}" class="entry-member__badge-text entry-member__badge-text--recurring">定</text>
    <text wx:if="{{entry.isShared}}" class="entry-member__badge-text entry-member__badge-text--shared">公</text>
  </view>
  ```
- `.entry-member__badge` 增加 `display: flex; gap: 2rpx;`
- 单字时视觉尺寸不变，双字时向左展开 ≈ 22rpx（一个字宽 + gap），不遮挡头像主体
- **顺序固定"定 公"**（不因用户勾选顺序而变），保持全 App 一致

### 6.5 明细页长按菜单

**不为定时生成的流水做任何额外处理**。"定"字角标已足以让用户识别流水来源；长按菜单保持与常规流水完全一致，不注入任何"来源信息条"，避免为一个已经清晰可见的属性添加冗余的文字提示。

## 7. 边界情况与产品决策

| 情况 | 决策 | 理由 |
|---|---|---|
| 分类被用户删除 | 规则自动降级到该分类的一级分类；一级也被删则降级到"其他"，并在列表页顶部黄条提示"N 条规则因分类变更已降级" | 不阻塞跑账 |
| 账本被删除 | 规则**自动禁用**，列表页红字提示"账本已删除，请编辑规则或删除" | 避免默默失败 |
| 用户退出家庭 / 被移出家庭 | 该用户在该家庭账本下的定时规则**自动禁用**，列表页红字提示 | 权限已失，且规则跟随用户而非账本 |
| 用户从个人账本切换为协作账本，或反之 | **不影响**已有规则（规则本身有 `ledger_id`，与用户当前 active ledger 无关） | 归属模型的核心保证 |
| 服务器宕机错过执行时间 | 恢复后**最多补 1 次最近一次的错过窗口**（≤ 24h 内的），超过 24h 不补，且不写入任何"漏了 N 次"的通知 | 静默 |
| 规则在同一天匹配到多个规则的执行时段（例如凌晨窗口内有 3 条） | 后台错峰调度保证每条规则的分钟点不同，用户体验上就是"今天凌晨陆续记了 3 条"，各条 `occurred_at` 都在其分配的时点 | 用户看到的流水时间 = 实际执行时间 |
| 用户临时不想记某个月 | 到明细页删除该条自动生成的 entry 即可（entry 与手记 entry 完全一致，可删可改）；或者临时禁用该规则 | 二选一 |
| 用户设了两条完全一样的定时 | 允许，不强行合并；列表页显示两条 | 合并策略易误伤"每月两次工资"这类真实场景 |
| 生成 entry 时 ledger.currency 与规则里保存的 currency 不一致 | 以**规则保存时的 currency** 落账；不做转换，audit_log 留痕 | 简单胜过智能；MVP 阶段单币种，这个场景实际不发生 |
| 用户复制规则后，与原规则完全一致 | 允许保存；不主动去重 | 与"设了两条一样定时"同理 |

## 8. 生成的流水行为

### 8.1 数据落地
- 生成的 entry 与用户手记的 entry **在 ledger 页、统计、预算、审计中一致对待**。
- 但 entry 需带一个内部字段 `source_recurring_id`，用于：
  1. 明细页展示 §6 定义的"定"字角标
  2. 统计侧不做区分（用户维度视角一致）
  3. 审计侧留痕

### 8.2 修改历史生成的 entry
- 允许用户编辑 / 删除历史生成的 entry（与普通 entry 完全一致），**不会**影响后续定时执行。
- 修改**不回写**到定时模板（避免"用户改了一次金额，就以为以后都变了"的心智负担）。

### 8.3 幂等
- 同一规则同一"执行周期日"最多生成一条 entry。技术上通过 `(recurring_id, next_run_at_date)` 唯一约束保证，重复触发（例如调度重试）不会重复生成。
- 同一规则的多个被勾中的日子（如"每周一、三、五"），三条 entry 各自幂等，`client_ref_id` 各不相同。

  2. `recurring_rules` 主键索引从"按 ledger 查询"改为"按 created_by 查询"

     - `days_of_week SMALLINT[]` · 每周 / 每两周用 · CHECK `1 <= cardinality(arr) <= 7`
     - `days_of_month SMALLINT[]` · 每月 / 每两月 / 每三月用 · CHECK `1 <= cardinality(arr) <= 14`
     - **每年的跨月表达**：不能再用"一个 month + days 数组"表达（因为要跨月）。推荐用 `year_month_days INTEGER[]`，每个元素编码为 `month * 100 + day`（例如 1/1 → 101, 12/25 → 1225）；CHECK `1 <= cardinality(arr) <= 12`；每个元素校验 `month ∈ [1,12] AND day ∈ [1, days_in_month(month)]`（2 月允许到 29）。这样 SQL 端就能用一个 array 表达 "1/1、2/2、…、12/12" 这种规则
  7. `computeNextRunAt` 需要遍历数组：给定 `from`，找出所有被勾中的日子在当次周期里的实际落地日（含 31→月末回落 + 每年跨月 2/29→2/28 平年回落），选最小 > from 的落地日；若当次周期空跑则推进到下一周期
