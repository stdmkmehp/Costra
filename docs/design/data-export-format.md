# 数据导入/导出格式设计

> 状态：已实现（v1 脚本版）  
> 适用版本：v0.2+  
> 实现方式：后台脚本（不经客户端）

---

## 一、设计目标

1. **人类可读**：用户拿到 CSV 后可以在 Excel / WPS / Numbers 中直接打开查看
2. **可逆导入**：导出格式作为标准交换格式，同格式文件可导回系统
3. **兼容主流**：对齐随手记、微信支付账单等常见导出格式，降低用户迁移门槛
4. **脚本优先**：v1 版本在服务器端通过 CLI 脚本执行，不暴露 HTTP 接口

---

## 二、导出文件格式

### 2.1 文件规格

| 属性 | 值 |
|---|---|
| 格式 | CSV（RFC 4180） |
| 编码 | UTF-8 with BOM（兼容 Excel） |
| 行结尾 | CRLF |
| 分隔符 | 逗号 `,` |
| 引用 | 含逗号/换行/引号的字段用双引号包裹 |
| 文件名 | `{账本名}_{起始日期}_{结束日期}.csv` |
| 示例 | `我的账本_2026-01-01_2026-06-10.csv` |

### 2.2 列定义

| 序号 | 列名 | 类型 | 说明 | 示例 |
|---|---|---|---|---|
| 1 | 记录ID | TEXT | entry UUID，导入时用于去重 | `019059a7-...` |
| 2 | 账本ID | TEXT | ledger UUID | `01905abc-...` |
| 3 | 记账人ID | TEXT | user UUID（`created_by`） | `01904def-...` |
| 4 | 日期 | TEXT | ISO 日期 `YYYY-MM-DD` | `2026-06-10` |
| 5 | 时间 | TEXT | 24h 格式 `HH:mm` | `14:30` |
| 6 | 类型 | TEXT | `支出` / `收入` / `转账` | `支出` |
| 7 | 一级分类 | TEXT | 一级分类名称 | `餐饮` |
| 8 | 二级分类 | TEXT | 二级分类名称 | `外卖` |
| 9 | 金额 | NUMBER | 正数，单位：元，两位小数 | `35.50` |
| 10 | 币种 | TEXT | ISO 4217 货币代码 | `CNY` |
| 11 | 账户 | TEXT | 预留，当前留空 | |
| 12 | 转入账户 | TEXT | 预留，当前留空 | |
| 13 | 归属 | TEXT | `共同` / `个人`，仅支出有值 | `共同` |
| 14 | 记账人 | TEXT | 用户昵称（人类可读，不参与导入逻辑） | `小赵` |
| 15 | 备注 | TEXT | 用户填写的备注 | `公司楼下` |

> **账户 / 转入账户**：accounts 功能当前未实装，导出时留空，导入时忽略。待账户功能上线后补充。

## 三、UUID 策略

### 3.0 系统 UUID 规则

Costra 所有实体 ID 使用 **UUID v7**（RFC 9562）：
- **48-bit 毫秒时间戳** + **74-bit 随机位** = 122 位有效熵
- 应用层生成（`server/src/id/idGen.ts` → `uuidv7` 库）
- 特征：前 12 个 hex 字符编码了创建时间，天然按时间递增排序

### 3.1 场景一：外部平台数据导入（无原始 UUID）

从随手记、微信支付账单等外部平台导入的数据没有 Costra 的记录ID。处理方式：

**CSV 中 `记录ID` 列允许留空**（调整：该列从"必填"改为"条件必填"）：

| 情况 | 处理 |
|---|---|
| `记录ID` 非空 | 按该 UUID 入库（用于 Costra 自身导出再导入的场景） |
| `记录ID` 为空 | 脚本自动生成 UUID v7 并填入，生成时间取该行的 `日期+时间` 作为时间戳基准 |

**为什么用行数据的时间而非当前时间**：UUID v7 的时间戳部分影响排序。若 2024 年的账单用 2026 年时间戳生成 ID，会导致 entry 按 ID 排序时与 `occurred_at` 不一致。因此脚本在生成 UUID 时，将该行的 `occurred_at`（日期+时间）作为 UUID v7 的时间戳分量，随机位仍随机生成。

**去重注意**：对于 `记录ID` 为空的行，由于是新生成的 UUID，永远不会与现存记录重复，全部作为新增处理。重复导入同一份外部文件时，会产生重复记录。建议：
- 脚本在导入完成后输出生成的 UUID 映射表（行号 → 生成的ID），供用户存档
- 用户如需重新导入，应先删除上次导入的记录，或使用带 `记录ID` 的版本

### 3.2 场景二：UUID 碰撞风险分析

**Costra 导出再导入**：`记录ID` 就是 entries 表中的 `id`，导入时直接用于去重匹配，不存在碰撞问题。

**自动生成 UUID 与现存记录碰撞**：
- UUID v7 有 74-bit 随机位（约 1.88 × 10²² 种组合）
- 假设数据库已有 100 万条记录，新生成 1 条 UUID 碰撞概率 ≈ 5.3 × 10⁻¹⁷
- 即使导入 10 万条，碰撞概率 ≈ 5.3 × 10⁻¹²（万亿分之五）
- **结论：碰撞概率可忽略，无需额外防碰撞机制**

**防御性措施**（虽然概率极低，仍做兜底）：
- 入库时使用 `INSERT ... ON CONFLICT (id) DO NOTHING`
- 若发生冲突（理论上不会），重新生成 UUID 并重试一次
- 导入报告中标注该行为 WARNING：`UUID碰撞已自动重新生成`

## 四、导入解析规则

### 4.1 必填列与校验

导入时至少需要以下列才能生成合法 entry：

| 列 | 必填 | 缺省逻辑 |
|---|---|---|
| 记录ID | ⚠️ 条件 | 为空时自动生成 UUID v7（见 §3.1） |
| 账本ID | ✅ | — |
| 记账人ID | ✅ | — |
| 日期 | ✅ | — |
| 类型 | ✅ | — |
| 金额 | ✅ | — |
| 一级分类 | ✅ | — |
| 二级分类 | ❌ | 匹配一级分类下 `sort_order=1` 的子分类 |
| 时间 | ❌ | 默认 `12:00` |
| 币种 | ❌ | 默认 `CNY` |
| 账户 | ❌ | 忽略（功能未实装） |
| 转入账户 | ❌ | 忽略（功能未实装） |
| 归属 | ❌ | 支出默认 `共同` |
| 记账人 | ❌ | 仅展示用，不参与逻辑 |
| 备注 | ❌ | 留空 |

### 4.2 导入前校验（逐行）

每行数据在入库前必须通过以下全部校验，**任一失败则该行记为错误、不入库**，错误信息写入 `_errors.csv`（含行号 + 失败原因）。

#### A. 文件级校验（解析 CSV 前）

| # | 校验项 | 失败处理 |
|---|---|---|
| A1 | 文件存在且可读 | 终止，报错退出 |
| A2 | 编码为 UTF-8（可带 BOM） | 终止，报错退出 |
| A3 | 首行表头包含所有必填列名（`账本ID`, `记账人ID`, `日期`, `类型`, `金额`, `一级分类`）；`记录ID` 列必须存在但值可为空 | 终止，报缺失列名 |
| A4 | 文件至少有 1 行数据（除表头外） | 终止，报空文件 |
| A5 | CSV 格式合法（引号闭合、列数一致） | 解析异常行记为错误，其余行继续 |

#### B. 行级校验 — UUID 合法性

| # | 校验项 | 失败原因示例 |
|---|---|---|
| B1 | `记录ID` 若非空，须符合 UUID 格式（8-4-4-4-12 hex） | `记录ID格式非法: "abc123"` |
| B2 | `记录ID` 若为空，自动生成 UUID v7（时间戳取该行 `日期+时间`） | （不报错，自动处理） |
| B3 | `账本ID` 非空 | `账本ID为空` |
| B4 | `账本ID` 符合 UUID 格式 | `账本ID格式非法` |
| B5 | `记账人ID` 非空 | `记账人ID为空` |
| B6 | `记账人ID` 符合 UUID 格式 | `记账人ID格式非法` |
| B7 | 所有非空 `记录ID` 在 CSV 内不重复 | `记录ID在CSV内重复（行X与行Y）` |
| B8 | 自动生成的 UUID 与 CSV 内其他已有/已生成的 `记录ID` 不重复 | （内部保证，无需用户关注） |

#### C. 行级校验 — 业务实体存在性（查库）

| # | 校验项 | 失败原因示例 |
|---|---|---|
| C1 | `记账人ID` 对应的 user 存在且 `deleted_at IS NULL` | `记账人不存在: 01904def-...` |
| C2 | `账本ID` 对应的 ledger 存在且 `deleted_at IS NULL` | `账本不存在: 01905abc-...` |
| C3 | 该 ledger 所属 family 中，`记账人ID` 为活跃成员（`family_members.left_at IS NULL`） | `用户01904def不是账本01905abc所属家庭的活跃成员` |

> **性能优化**：C1~C3 可先批量收集 CSV 中所有 distinct `记账人ID` + `账本ID` 组合，一次查库构建 allowSet，再逐行检查归属。

#### D. 行级校验 — 字段格式与取值

| # | 字段 | 校验规则 | 失败原因示例 |
|---|---|---|---|
| D1 | `日期` | 非空 + 可解析为 `YYYY-MM-DD` + 日历合法（如无 2026-02-30） | `日期格式非法: "2026/06/10"` |
| D2 | `时间` | 若非空，须匹配 `HH:mm`（00:00~23:59） | `时间格式非法: "25:00"` |
| D3 | `类型` | 非空 + 属于类型映射表（§4.5） | `类型无法识别: "退款"` |
| D4 | `金额` | 非空 + 解析后为正数（> 0） + 非 NaN/Infinity | `金额非法: "abc"` 或 `金额为0或负数` |
| D5 | `币种` | 若非空，须为 3 位大写字母（ISO 4217） | `币种格式非法: "rmb"` |
| D6 | `归属` | 若非空，须为 `共同`/`个人`/`shared`/`personal` | `归属值非法: "公共"` |
| D7 | `备注` | 长度 ≤ 200 字符 | `备注超长(203字符，限200)` |
| D8 | `金额` | 小数位 ≤ 2 位（解析后） | `金额精度超限: "35.567"` |

#### E. 行级校验 — 分类存在性

| # | 校验项 | 失败处理 |
|---|---|---|
| E1 | `一级分类` 非空 | 该行报错 |
| E2 | `一级分类` 在目标 family 分类或系统分类中存在，且 `type` 匹配（expense 分类不能用于 income 行） | 该行报错：`一级分类"xxx"在该账本下不存在` |
| E3 | 若 `二级分类` 非空，须为该一级分类的子分类 | **降级处理**：归入该一级分类下 `sort_order=1` 的默认子分类，报告中标注 warning |
| E4 | 若 `二级分类` 为空 | 正常：取该一级分类下 `sort_order=1` 的默认子分类 |

> **注意**：E2 的 type 交叉校验很重要——不允许把一个 expense 的一级分类（如"餐饮"）用在 income 类型的行上。

#### F. 行级校验 — 业务逻辑一致性

| # | 校验项 | 失败原因示例 |
|---|---|---|
| F1 | 若 `类型` = `转账`，一级分类须为"转账" | `转账类型的一级分类必须为"转账"` |
| F2 | 若 `类型` ≠ `支出`，`归属` 列应为空（收入/转账无归属概念） | warning：`非支出类型的归属列将被忽略` |
| F3 | `日期` 不在未来（不超过当前日期 +1 天，容忍时区差异） | `日期在未来: 2027-01-01` |
| F4 | `日期` 不早于合理下限（如 2000-01-01） | `日期过早: 1970-01-01` |

#### 校验结果分级

| 级别 | 含义 | 处理 |
|---|---|---|
| **ERROR** | 该行数据不合法，无法入库 | 跳过该行，记入 `_errors.csv` |
| **WARNING** | 数据可入库但存在潜在问题 | 正常入库，记入导入报告的 warnings 部分 |

Warning 场景举例：
- 二级分类不存在但一级存在 → 降级到默认子分类
- 非支出类型填了归属 → 忽略归属值
- 分类 type 歧义由 `is_direct_default` 消歧 → 报告使用了哪个

### 4.3 分类匹配策略

导入时根据分类名称 + 类型双重匹配：

1. **Family 分类优先**：在 `账本ID` 对应 family 的自定义分类中查找（`categories.family_id = ledger.family_id` + `categories.type = 行类型`）
2. **系统分类回退**：未命中则匹配系统预设分类（`is_system = true` + `type` 一致）
3. **一级匹配**：`一级分类` 名称须精确匹配某个 `parent_id IS NULL` 的分类
4. **二级匹配**：
   - 非空时：在已匹配的一级分类下查找 `name` 精确匹配的子分类
   - 未找到 → WARNING，降级到该一级下 `sort_order = 1` 的子分类
   - 为空时 → 直接取 `sort_order = 1` 的子分类
5. **同名歧义**（一级分类名相同出现在 family 分类和系统分类中）：family 分类优先
6. **一级分类完全不存在** → ERROR，该行不入库

### 4.4 去重策略

- `记录ID` 非空时：
  - 系统中已存在相同 ID → **默认跳过**（不覆盖）
  - 系统中不存在 → 创建新记录
- `记录ID` 为空时（外部数据导入）：
  - 自动生成 UUID v7 → 作为新记录创建（无去重）
- 若需要覆盖已有记录，需显式指定 `--force-update` 参数：
  - 已存在相同 ID → 用 CSV 行数据**更新**该记录（`version + 1`，触发 `change_seq` 递增）
  - 不存在 → 创建新记录
  - `--force-update` 对 `记录ID` 为空的行无效（新生成的 UUID 不可能已存在）

### 4.5 类型映射

兼容多种写法：

| 导入值 | 映射到 |
|---|---|
| `支出` / `expense` / `花费` | `expense` |
| `收入` / `income` / `进账` | `income` |
| `转账` / `transfer` / `内部转账` | `transfer` |

### 4.6 金额解析

- 去除千分位逗号：`1,000.50` → `1000.50`
- 去除货币符号前缀：`¥35.5` → `35.5`
- 始终取绝对值（负号忽略）
- 精度：四舍五入到分（2 位小数），存入 DB 为 BIGINT（分）

## 五、脚本接口设计

> **约定：必须在宿主机执行**（`server/` 目录下运行 `npx tsx`）。
> PG 端口已映射 `127.0.0.1:5432`，脚本加载 `/data/conf/server.env` 后自动将 `@postgres:` 替换为 `@127.0.0.1:`。

### 5.1 导出

```bash
cd server && npx tsx scripts/export-entries.mts \
  --user-id <uuid> \
  --ledger-id <uuid> \
  --from 2026-01-01 \
  --to 2026-06-10 \
  [--output ./exports/] \
  [--env-file /data/conf/server.env]
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `--user-id` | ✅ | 导出哪位用户的记录（`created_by`） |
| `--ledger-id` | ✅ | 导出哪个账本 |
| `--from` | ✅ | 起始日期（含），`YYYY-MM-DD` |
| `--to` | ✅ | 结束日期（含），`YYYY-MM-DD` |
| `--output` | ❌ | 输出目录，默认 `./exports/` |
| `--env-file` | ❌ | 环境配置文件路径，默认 `/data/conf/server.env` |

脚本执行时会校验：user 存在 + user 是该 ledger 所属 family 的活跃成员。

### 5.2 导入

```bash
cd server && npx tsx scripts/import-entries.mts \
  --file ./imports/data.csv \
  [--dry-run] \
  [--force-update] \
  [--env-file /data/conf/server.env]
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `--file` | ✅ | 待导入的 CSV 文件路径 |
| `--dry-run` | ❌ | 仅校验并输出报告，不写入数据库 |
| `--force-update` | ❌ | 对已存在的 `记录ID` 执行覆盖更新而非跳过 |
| `--env-file` | ❌ | 环境配置文件路径，默认 `/data/conf/server.env` |

> 导入不再需要 `--ledger-id` 或 `--user-id` 参数，因为每行 CSV 中已包含 `账本ID` 和 `记账人ID`。
> 一个 CSV 文件中可以包含多个账本、多个记账人的数据，脚本会逐行校验归属关系。

## 七、安全与合规

1. **导出仅限后台操作**：v1 不暴露 HTTP 接口，由运维人员在服务器执行
2. **未来客户端导出前置条件**：
   - 用户需已绑定手机号（IA 设计要求）
   - 导出前二次确认弹窗
   - 导出文件包含水印（用户 ID + 时间戳）
3. **导入审计**：每次导入操作记录到 `audit_log`（操作人、时间、文件摘要、结果）
