## 一、R36 · 普通并发记账路径的 change_seq「已取号未提交」洞

### 1.1 缺陷陈述

客户端增量同步依赖 `entries.change_seq`（全库单调序列）+ 每个 family 维护一个 watermark（`GET /sync/pull?since=<change_seq>`）。缺陷在于：**序列的「取号」（`nextval`）与事务的「提交」（COMMIT）是两个顺序可能不一致的动作**。

```text
两笔普通记账并发：
  A 取号 seq=100（事务未提交）
  B 取号 seq=101（事务未提交）
      ↓ B 先 COMMIT
  客户端此刻 pull → 拿到 B → watermark 被推到 101
      ↓ A 才 COMMIT
  A 的 seq=100 < watermark(101) → A 永久落在 watermark 之后 → 客户端再也拉不到 A
```

**根因一句话**：watermark 直接采用了 `nextval` 的值，没有区分「号已分配」和「事务已提交」。

- `migration 0001`：`entries.change_seq BIGINT NOT NULL DEFAULT nextval('entries_change_seq')`，`UNIQUE(change_seq)`，索引 `idx_entries_ledger_change_seq (ledger_id, change_seq)`。
- `migration 0016`：`ALTER SEQUENCE entries_change_seq CACHE 1`。`CACHE 1` 只保证序列**单调**（恢复跨连接的严格递增），**不保证提交顺序**——这正是洞存在的本质：单调 ≠ 提交有序。
- 既有两条「补丁」都只覆盖**批量写入**路径，没碰普通记账：
  - L13 的 `sync_epoch`（`migration 0019`）：给运维直连 SQL 修复用的「事后清零重拉」重锤。
  - 导入/导出的 `sync-hold`（`migration 0021`）：导入取号前钉住 `ledgers.sync_hold_seq`，pull 期间钳制 `change_seq <= cap`。

### 1.2 影响面（失败场景发生条件 + 实际后果）

| 维度 | 评估 |
|---|---|
| **唯一消费者** | 所有依赖增量同步的客户端（每台设备 / 每个 family 成员各自维护 watermark） |
| **失败场景发生条件** | 两笔（或多笔）普通记账**并发**，且一次 `/sync/pull` **恰好插在两次 COMMIT 之间**。`entryService` 三条写路径（`create` / `update` / `softDelete`）都会触发取号，任一组合都可能命中 |
| **实际后果** | **高**：被落下的那条流水在该设备上**永久拉不到**。数据在服务端没丢（DB 里是完整的），只是这台客户端的本地视图从此缺一条。`findEntriesByFamilySince` 不过滤 `deleted_at`，所以连「补拉一次」都救不回来 |
| **发生概率** | **低**：单笔事务窗口是毫秒级，且需要 pull 恰好插在两次提交之间。多成员高频并发记账的家庭、弱网重试叠加的场景概率会升高 |
| **现状防护** | **无**：普通记账路径没有任何防护 |

### 1.3 为什么现在不修（决策背景）

导入/导出方案的 `sync-hold`（方案 D）是**「洞形成之前就让它不形成」**的机制：导入取号前用独立短事务把该 family 的 watermark 钉住，COMMIT 时与余额同语句原子解除。它只把「批量写入」这条路径堵死了，**刻意没动普通记账**——因为那要求改动 `entryService` 三条前台写路径（用户按下「保存」的那一刻），是另一份独立的、影响面更大的工程。

所以 R36 被登记为方案外 follow-up，等单独评估与排期。

### 1.4 根治方向（两条候选，可复用现有基建）

`sync-hold` 的 DDL 与 pull 侧钳制逻辑（`syncPullService` 按 `MIN(未过期 hold)` 钳制 `change_seq <= cap`）是**通用机制**，未来根治可直接复用。两条候选：

#### 方向 A · `entryService` 三条写路径挂「极短 hold」

让普通记账在取号时也挂一个**极短** `sync_hold`，与导入共用 `ledgers.sync_hold_seq` / `sync_hold_until` 两列 + pull 侧钳制逻辑。

- **优点**：机制与导入完全同构，复用率最高；pull 侧钳制代码零新增。
- **代价 / 风险**：把 hold 挂到**前台记账路径**上，每笔记账都要多一次 ledgers 行写 + 解锁。需评估：
  - 高频记账下的 ledgers 热点行锁竞争（hold 与余额更新现在是两条 UPDATE？还是要合并进 `applyBalanceDelta` 的同一语句？合并则又撞上「delta=0 时 short-circuit」的老坑）；
  - 极短 TTL 怎么取（普通记账事务毫秒级，TTL 可远小于导入的 120s）；
  - 失败路径 hold 泄漏的后果与自愈。

#### 方向 B · pull 改用「可见性快照」

pull 只下发 `change_seq < 当前最小活跃事务号` 的行——即不让 watermark 越过任何**尚未提交**的号段，从根上不依赖「提交顺序」。

- **优点**：不需要写路径配合，是读侧的纯防御。
- **代价 / 风险**：需要 PG 提供「当前最小活跃事务的 change_seq 下界」的可靠来源（如 `pg_current_snapshot()` / `txid_current_snapshot()` 的 xmin，但 `change_seq` 是应用层序列、与 `xmin` 不是同一坐标系，需要额外映射或改序列分配策略）。**坐标系对齐是本方向的核心技术风险**，需先做可行性验证。

### 1.5 验收判据（根治方案落地时必须满足）

1. **回归用例（核心，缺了无从验收）**：模拟「记账 A 取号 seq=100 未提交 → 记账 B 取号 seq=101 并先提交 → pull → A 提交 → pull」，断言**两轮 pull 合计覆盖 seq=100 与 101 的全部行**。同一用例在**移除根治机制的对照组**下必须失败（证明它真的在测洞，而不是恒真命题）。
2. **普通记账路径的性能不回归**：前台「保存」的 P99 延迟不因 hold / 快照而显著上升（需给出量化阈值）。
3. **hold / 快照失败路径的泄漏兜底**：任何异常路径（进程崩溃、DB 断连）最坏只让该 family 的 sync 延迟一个 TTL，**不得永久卡死**（沿用 sync-hold 的 H3 不变量）。
4. **导入路径不受回归**：现有 sync-hold 的 H1~H4 不变量测试保持原样，**不得放宽断言**。

> ⚠️ **测试通道前置依赖**：上述回归用例需要**同时持有两个未提交事务 + 一次独立 pull 连接**，pg-mem 无法真实模拟跨事务可见性（这正是 R33「真 PG 集成测试通道」缺失的同一后果）。**R36 的根治若要可验证，需先解决 R33**（建真 PG 测试通道，或明确登记「已接受风险」）。两个课题存在依赖关系，排期时须一并考虑。

## 二、R37 · 客户端本地库无 storage 配额超限降级分支

### 2.1 缺陷陈述

`miniprogram/services/db.ts` 是客户端本地库的写入口（经 `setItemStrict` 走 `wx.setStorage`）。微信对小程序本地存储有硬配额：**单 key 上限 1MB、总量上限 10MB**。当前 `db.ts` **没有针对配额超限的降级分支**——超限时的行为是未定义的。

### 2.2 影响面

| 维度 | 评估 |
|---|---|
| **唯一消费者** | 所有依赖本地库读写的客户端功能（流水月索引、实体缓存、outbox 等） |
| **失败场景发生条件** | 本地缓存累计逼近单 key 1MB 或总量 10MB。**典型触发 = 新设备首登老账号**：全量重拉历史流水，逐月写月索引 + 逐条写实体 key，最容易在「历史长 + 设备多成员」的账号上撞顶 |
| **实际后果** | **中**：超限后 `wx.setStorage` 抛错 / 失败，`setItemStrict` 不吞错会向上抛，但**没有降级的「腾空间」逻辑**（如淘汰最旧月份、清非关键缓存），用户侧表现为本地数据写不进去、同步卡住或反复失败 |
| **现状防护** | 仅 `setItemStrict` 的「失败抛错不吞」（防假绿），**没有配额维度的预防 / 降级** |

### 2.3 为什么现在不修（决策背景）

- 导入/导出方案的 `sync-hold` 取消了「全量重拉」（R26 随之消解），**导入不再是逼近配额上限的场景**——所以本方案**不再依赖**这条修复。
- 但配额缺口本身**仍然存在**：新设备首登老账号的全量拉取、长期高频记账的月索引累积，都在持续逼近上限。这是与导入无关的既有缺口，登记为独立 follow-up。

### 2.4 根治方向（候选）

围绕「单 key 1MB + 总量 10MB」两条约束，候选手段（可组合）：

1. **超限检测 + 优雅降级**：写前估算 / 写时捕获配额错误，触发降级（淘汰最旧月份的月索引 / 清可重建的派生缓存），而不是直接抛错卡死。
2. **大 key 分片**：对可能超 1MB 的月索引（长月份流水多）做 key 级拆分，绕开单 key 上限。
3. **容量水位监控**：周期性 `wx.getStorageInfo()` 上报 / 本地预警，逼近阈值时提前降级。
4. **明确「可牺牲数据」白名单**：区分「权威数据（需保留）」与「派生 / 可重建缓存（可淘汰）」，降级只动后者。

> 需先确认微信当前的真实配额口径（基础库 3.8.12+ 是否仍是 1MB/10MB，或已上调），再定降级阈值。**D2 纪律：配额阈值须附算术依据**（如「月索引单 key = 单条 N 字节 × 单月流水上限」）。

### 2.5 验收判据

1. **配额超限有可预期的降级行为**：构造逼近 / 超过单 key 与总量上限的用例，断言不卡死、不静默丢权威数据。
2. **派生缓存可安全淘汰**：被淘汰的缓存能从服务端 / 本地权威数据重建，重建路径有测试覆盖。
3. **无静默假绿**：超限与降级的中间态不能表现为「以为写成功实际没写」（沿用 `setItemStrict` 不吞错的红线）。

## 三、评审与验收纪律

- 两条课题**彼此独立**，可分别立项、分别排期；R36 的回归测试依赖 R33（真 PG 通道），**排期时把 R33 一并纳入考量**。
- 评审定级前必须先验证害处真实存在（**禁止先射箭后画靶**）；判断某列 / 某机制语义时须读**所有写它的 SQL / 代码**（尤其 UPDATE 的 SET 子句），不能只读 WHERE。
- 所有时间 / 次数 / 容量阈值参数须附**算术依据**（D2 纪律）；可查证事项（如微信当前配额口径）**先查证再登记**，不留「待确认」空转（D3 纪律）。
