# 记账小票（Receipt Share Card）v0.3

> **卡号**: COSTRA-2xx（待分配） · **Owner**: Product/Design/MiniApp
> **归属**: 分享卡片体系 [`README.md`](./README.md) 第 5 张卡片（slug `receipt`）
> **一句话**: 用户把「今天/本周/本月的记账」生成一张仿热敏纸小票大图，保存或直接发到微信对话；好友长按识别图内小程序码进入 Costra。核心目标是**满足分享欲 + 拓宽推广渠道**。

---

## 0. 为什么这张卡与其他 4 张不同（先讲清楚）

现有 4 张分享卡（family-invite / annual-report / entry-flex / budget-kept）都是**微信原生分享缩略图**（`onShareAppMessage` 的 `imageUrl`，5:4 或 1:1），受 [`safe-zone.md`](./safe-zone.md) 约束，且**禁止二维码浮层**（微信规范：分享缩略图带码会被判诱导、影响过审）。

记账小票是**两种图片用途的组合**，必须区分清楚，否则会踩微信规范红线：

| 图片 | 用途 | 承载二维码? | 走哪条链路 | 受 safe-zone 约束? |
|---|---|---|---|---|
| **① 小票大图**（本卡主角） | 用户「保存到相册」或在对话里**当作一张图片发出去** | ✅ 右下角小程序码 | `wx.showShareImageMenu` / `saveImageToPhotosAlbum` | ❌ 不受（它不是分享缩略图，是一张普通图片） |
| **② 分享缩略图** | 用户点原生「分享给朋友」时的**小程序卡片缩略图** | ❌ 严禁 | `onShareAppMessage.imageUrl` | ✅ 受，复用现有静态 png |

> **合规基石**：二维码只出现在「①小票大图」上。这张图在微信里是以**图片消息**形式传播（好友长按识别码），不是小程序卡片，因此不违反「分享缩略图禁二维码」的规范。原生小程序卡片分享（②）走点击直达、不带码，另行保留。

## 1. 产品定位与目标

### 1.1 用户价值
- **炫耀/记录欲**：把"我今天/这周/这个月花了啥"变成一张有设计感、有梗的小票，值得晒。
- **仪式感**：仿真实热敏纸小票（锯齿、点阵字、合计栏），把枯燥的记账数据变成有温度的"消费凭证"。

### 1.2 业务目标（可度量）
| 指标 | 定义 | 埋点 |
|---|---|---|
| 生成率 | 生成小票 UV / 统计页 UV | `receipt.generate` |
| 分享率 | 分享/保存 PV / 生成 PV | `receipt.share`、`receipt.save` |
| 拉新回流 | 从小票码/卡片进入的新用户 | `?from=share&card=receipt` scene 归因 |

### 1.3 非目标（首版明确不做）
- ❌ 任意日期/日历选择器（见 §2 决策）
- ❌ 单笔明细逐条列出（小票是**分类聚合**视图，不是流水导出）
- ❌ 多主题/多配色皮肤（首版单一"经典热敏纸"主题，A/B 预留见 §9）
- ❌ 年度小票（年度已有 `annual-report` 卡承接）

## 2. 周期模型（关键产品决策）

**决策：不提供任意日期选择，只开放 6 个「相对周期」预设枚举。**

理由：分享欲的本质是"新鲜的即时炫耀"，用户愿意分享的几乎都是最近的记账；任意选择器会引入日历组件、跨月跨年边界、空周期等复杂度与体验坑，投入产出比极低。预设枚举既覆盖 95% 场景，又天然规避"选到没数据的日子生成空小票"的尴尬。

| # | 枚举 `period` | 展示标题 | 数据区间（Asia/Shanghai） |
|---|---|---|---|
| 1 | `today` | 今天 · M月D日 | 当日 00:00 ~ 24:00 |
| 2 | `yesterday` | 昨天 · M月D日 | 昨日 00:00 ~ 24:00 |
| 3 | `this_week` | 本周 · M.D–M.D | 本周一 00:00 ~ 今天（自然周，周一起） |
| 4 | `last_week` | 上周 · M.D–M.D | 上周一 ~ 上周日 |
| 5 | `this_month` | 本月 · YYYY年M月 | 当月 1 日 ~ 今天 |
| 6 | `last_month` | 上月 · YYYY年M月 | 上月 1 日 ~ 月末 |

- **默认选中 `today`**（进入即可生成，减少一步）。
- 顶部用一排横向 `segment / chip` 切换，切换即时重算预览。
- 空数据周期（如今天还没记账）：不禁用，改为**"空小票"文案**（见 §5.5），依然可生成分享（"今天还没开张，明天加油"也有梗）。

## 3. 数据来源与聚合策略（对齐现有接口，尽量不改后端）

调研结论：后端只有 `monthly` / `yearly` 聚合，**无日/周聚合**。方案用"月度接口 + 前端二次聚合"实现全部 6 个周期，首版**无需新增后端聚合接口**。

### 3.1 取数入口（复用现有）
- `statisticsApi.getMonthlyStatistics(familyId, month, { topN, userId })` → 拿 `daily_trend[]`、`category_ranks[]`、`totals`。
- `entriesApi.fetchMonthEntries({ ledgerId, month, ... })` → 拿整月单笔 `Entry[]`（含 `category_id / amount / type / occurred_at / shared_type`），用于**日/周的按分类聚合**（monthly 的 category_ranks 是整月口径，不能直接切到某日/某周）。
- `ledgerBalanceApi.getCachedLedgerBalance / fetchLedgerBalance` → 可选的"当前账户结余"兜底展示。

### 3.2 各周期聚合策略
| 周期 | 数据来源 | 聚合方式 |
|---|---|---|
| `this_month` / `last_month` | `getMonthlyStatistics` | **直接用**其 `totals` + `category_ranks`（口径完全对齐） |
| `today` / `yesterday` | `fetchMonthEntries`(当月) | 本地按 `occurred_at` 过滤到目标日，再**按 category_id 分组求和**，套 category meta 拿名字/图标 |
| `this_week` / `last_week` | `fetchMonthEntries`(可能跨 2 个月) | 本地按自然周过滤，按 category 分组求和；**跨月的周拉相邻两个月合并** |

### 3.3 前端聚合模块（新增）
新增 `miniprogram/services/receiptData.ts`（纯函数 + 取数编排）：
```
buildReceiptData(period, ctx) -> ReceiptData
```
其中 `ReceiptData`（供渲染层消费，金额单位 cents）：
```
{
  period_label: string          // "本月 1–27 日"
  ledger_name: string           // "我们家"
  issued_at: Date               // 出票时间
  range_start / range_end: Date
  totals: { expense, income, balance, entry_count }
  lines: Array<{ name, amount, count, merged_count? }>  // 降序；merged_count 表示"其他 N 类"
  insight: string               // "共 23 笔 · 日均 ￥87.03"
  punchline: string             // "最能花在「餐饮」· 占 53%"
  is_empty: boolean
}
```
> **注意**：`lines` **不含 `icon` 字段** —— 视觉设计 D1 已确定去掉分类图标（热敏纸单色不可能印彩色 emoji，且 canvas 绘 emoji 跨端差异大）。分类仅用文字名。
- **口径统一**：严格复用 `statisticsService` 的口径注释——时区 Asia/Shanghai、金额整数 cents、transfer 不计、`shared_type IS NULL` 的 expense 不计（与 family summary 一致）。日/周本地聚合必须套用同一过滤规则，避免与统计页数字对不上。
- **分类合并**：小票行数上限（如 8 行），超出部分合并为"其他 ￥xxx"，保证热敏纸版式不溢出。
- 金额格式化统一走 `utils/money.ts`（禁止 float）。

### 3.4 刷新与缓存
- 页面订阅 `SYNC_DONE` / `ENTRY_SAVED` / `ENTRY_UPDATED` / `ACTIVE_FAMILY_CHANGED`，记账后失效当前周期缓存并重算预览（避免小票数据滞后）。
- 优先读 `getCachedMonthly` / `getCachedLedgerBalance` 秒出预览，后台 `fetch*` 校准（SWR，与统计页一致）。

## 4. 二维码（小程序码）方案

用户提供的物料是 **COSTRA 圆形小程序码 + 右下小程序标**（保存后长按识别 / 群聊传播用）。

### 4.1 首版：静态码打包（✅ 已决策采用）
- 将该小程序码裁切导出为 `miniprogram/assets/share/receipt-qrcode.png`（建议 @3x，**白底方形裁切**以贴合热敏纸浅色区；素材右下角的绿色小程序标保留 —— 它是全图唯一彩色，见 §5.0）。
- 优点：零后端成本、离线可用、生成即可用。
- 缺点：所有小票同一个码，无法按用户/scene 归因到"是谁分享带来的新用户"。**已显式接受此权衡**（首版只看总量转化）。

### 4.2 二期（可选）：动态码带归因
- 若要精确归因，新增后端 `wxacode` 接口（微信 `getUnlimitedQRCode`，`scene` 塞 `inviter_uid` 或 `card=receipt`），前端按需拉取带 scene 的码。
- scene 长度受限（32 字符），需短码映射；有额度/QPS 成本。**首版不做**，留待验证转化后再上。

### 4.3 码在小票上的位置
- 固定在小票**底部锯齿之上、右下角**，尺寸 ~140rpx，旁边一行 caption「长按识别 · 一起用 Costra 记账」。
- 因为是完整大图（非缩略图），不违反微信规范。

## 5. 视觉设计（仿真实热敏纸小票）

### 5.0 设计立意：单色油墨 + 唯一一抹绿

**核心原则（v0.2 修订，推翻 v0.1 的双色合计）**：

真实热敏打印在物理上**只有一种显色**，不存在彩色。一旦给"合计支出/收入"上莫兰迪双色，"仿真凭证"的质感会瞬间垮掉，退化成"一张加了锯齿边的普通数据卡"。因此：

> **整张小票=单色油墨（暖黑 `#1c1b1a` 的不同浓度）。全图唯一的彩色，来自右下角小程序码自带的那一抹微信绿徽标。**

这不是妥协，而是三重收益：
1. **物理真实**：单色=热敏纸的本质，质感立住。
2. **视觉焦点**：全图仅一处彩色 → 视线必然被引导到二维码，**推广目标反而被强化**。
3. **克制高级**：符合项目"油墨暖黑 + 暖灰白"的二元基调（`design_spec.md §2`），不与主 App 视觉打架。

**莫兰迪双色（`#AC7B6C`/`#8FAA83`）在本卡不使用** —— 它们的 token 注释明确写着"年度页月度流水线条可视化专用"，跨组件复用违反项目约定。收支的区分改用**排版层级 + 正负号**表达（见 §5.4）。

### 5.1 画布规格
| 项 | 值 |
|---|---|
| 逻辑宽度 | **750rpx**（满宽） |
| 纸张宽度 | **622rpx** 居中（左右各留 64rpx "桌面"留白，让纸有"漂浮在桌上"的实物感） |
| 纸内版心 | 纸张内左右各 **48rpx** padding → 内容区 **526rpx** |
| 高度 | **内容自适应**，典型 1040~1420rpx |
| 导出倍率 | 3x（2250px 宽），保证微信压缩后仍清晰 |
| 安全区 | 不套 5:4 缩略图安全区（本图是图片消息，非分享缩略图） |

**为什么纸不做满宽**：满宽会像"一个页面"，留出桌面留白才像"一张纸"。这是仿真质感的关键一步。

### 5.2 材质三层（由下至上绘制）
1. **桌面底**：`#e8e6df`（比纸略深的暖灰，制造纸张浮起的对比）。
2. **纸张**：`#faf8f2`（热敏纸米白，比 token `boneWhite #f1f2ec` 更暖更亮 —— 热敏纸是偏白的）。
   - 纸张**不加圆角**（真实小票是直角裁切）。
   - 纸张投影：`rgba(0,0,0,0.10)` blur 24 offsetY 6，极轻，仅够托起纸张。**不用 `shadow.subtle`**（3px 5px 30px 0.22 太重，会脏）。
3. **纸纹噪点**：整纸叠加 2%~3% 不透明度的细颗粒噪点（随机点阵），破除数字化的"过分干净"。**这是廉价感与高级感的分水岭**。

### 5.3 撕边（锯齿）规格
- 顶/底均为撕边，**波形不同**：
  - 顶部：`triangle` 三角齿，齿宽 **16rpx**、齿高 **10rpx**（打印机切纸的规整齿）。
  - 底部：同参数但**相位偏移半齿 + 每齿高度 ±2rpx 随机抖动**（手撕的不规则感）。
- 齿必须**镂空**（露出桌面底色），不是画在纸上的三角形。实现：绘制纸张路径时把齿形并入 path。

#### 关键设计决策逐条说明

| # | 决策 | 理由 |
|---|---|---|
| D1 | **去掉分类 emoji 图标** | v0.1 用 🍜🚇🛒。但 ①热敏纸不可能印彩色 emoji，破坏质感；②canvas 绘 emoji 各端渲染差异大（R5 风险）；③纯文字分类名反而更像真凭证。**改为纯文字左对齐**。 |
| D2 | **分类行增加"笔数"中栏** | 只有金额显得单薄。"餐饮 12 笔 1,240.00"信息密度更高、更像消费清单，且笔数用 28% 浓度弱化，不抢金额。 |
| D3 | **金额去掉 `￥` 前缀（仅分类行）** | 真实小票的清单区只印数字。`￥` 只在"合计/支出/收入/结余"出现，形成层级。 |
| D4 | **合计区拆成"合计"小标题 + 三行** | 支出 64rpx 是全图最大字（视觉锚点），收入 44rpx 次之，结余 48rpx 用实线分隔后单列 —— 靠**字号阶梯**而非颜色区分收支。 |
| D5 | **收入用 `+` 正号** | 单色下区分收支的唯一手段。支出不加 `-`（小票语境下支出是默认项，加负号反而怪）。 |
| D6 | **"其他 N 类"而非"其他"** | 明确告知被合并了几类，避免"数字对不上"的疑虑（呼应 R2 信任风险）。 |
| D7 | **梗行放最后、带占比** | "最能花在「餐饮」· 占 53%" —— 有具体数字才有说服力和传播力，纯形容词很空。 |
| D8 | **三种分割线各司其职** | 点线(装饰/品牌区)→虚线(清单分隔)→实线(合计强分割)。层级清晰，也是真实小票的常见做法。 |
| D9 | **码区左对齐、文案在右** | 码放正右下角会显得像"贴上去的广告"；左对齐 + 右侧两行文案，形成一个完整的"签章区"。 |
| D10 | **日均而非平均每笔** | "日均 ￥87.03" 对用户更有感知（可对比生活成本），"平均每笔"太统计学。日周期时改为"共 N 笔"。 |

| 品牌署名 | 20rpx | 400 | 28% | |

- **所有金额必须等宽数字（tnum）**：canvas 中通过 `ctx.font` 指定等宽字族兜底（如 `"DIN Alternate", "SF Mono", Menlo, monospace`），或**逐字符定宽绘制**保证小数点对齐。金额不对齐是"假凭证"最明显的破绽。
- **浓度=单色透明度**：统一 `rgba(28,27,26,α)`，α ∈ {1.0, 0.48, 0.28, 0.16, 0.12}。这是单色体系的浓淡语言，直接复用 token `role.text.*` 的既有档位。

#### 5.5.1 抬头拼接规则（账本名是用户自由文本，必须处理边界）

抬头格式：`<账本名> + 小票`，居中，字距 +4rpx。例：`我们家小票`、`老王家小票`。

| 场景 | 处理 |
|---|---|
| 正常（≤ 6 字） | 直接拼接 `我们家小票`，字距 +4rpx |
| 偏长（7~10 字） | 保留全名，**字距降为 +2rpx**，字号降 24rpx |
| 过长（> 10 字） | 账本名截断至 9 字 + `…`，再拼 `小票` |
| 名字已含"小票"二字 | **不重复拼接**（如账本名"小票测试"→ 直接显示"小票测试"），避免"小票测试小票" |
| 名字含"账本/家庭"后缀 | 正常拼接，不做特殊处理（"我们家账本小票"可接受） |
| 账本名为空/加载失败 | 兜底显示 `记账小票` |
| 个人默认家庭 | 账本名通常为用户昵称或"我的账本"，正常拼接 |

- 拼接后仍须走 §6.4 C3 的 `truncate()` 二次保护，确保不超版心宽度（526rpx）。
- 字距通过逐字符绘制实现（canvas 无 `letter-spacing`），见 §6.4 C4。

### 5.10 梗行文案矩阵（自嘲基调）

**基调定义**：**自嘲 > 攻击**。锋利，但刀口向内。

#### 三条铁律（不可违反）

| # | 铁律 | 原因 |
|---|---|---|
| T1 | **自嘲的箭头只能指向"我"或"钱包"，绝不能指向具体的人** | Costra 是**家庭共享账本**。任何指向他人消费的调侃（如"某人又买了 ￥800 化妆品"）会引发**真实家庭矛盾**，让产品变成吵架导火索。**禁止在梗行出现任何成员昵称**。 |
| T2 | **不评判消费是否"应该"** | 不写"这钱花得不值""又乱花钱"。用户消费不接受道德审判，只做**事实的幽默化表达**。 |
| T3 | **不用焦虑/恐吓话术** | 不写"再这样下去要破产""你的钱包在哭"。目标是激发分享欲，不是制造焦虑。 |

#### 文案选取规则（数据驱动，按优先级匹配，命中即用）

不是随机文案，而是**由数据特征挑选**，这样才有"被说中了"的分享冲动：

| 优先级 | 触发条件 | 文案模板 | 示例 |
|---|---|---|---|
| P1 | 支出=0（空小票） | `零消费 · 今天我是自己的英雄` | — |
| P2 | 单一分类占比 ≥ 70% | `我基本上只是<分类>的搬运工` | `我基本上只是餐饮的搬运工` |
| P3 | 单一分类占比 ≥ 50% | `<分类>又赢了 · 吃掉 <N>%` | `餐饮又赢了 · 吃掉 53%` |
| P4 | 最大单笔 ≥ 总支出 40% | `一笔 ￥<M> 干掉小半个月` | `一笔 ￥1,280 干掉小半个月` |
| P5 | 结余 < 0（入不敷出） | `收支逆差 · 请假装没看见` | — |
| P6 | 笔数 ≥ 30 | `记了 <N> 笔 · 记账比赚钱勤快` | `记了 61 笔 · 记账比赚钱勤快` |
| P7 | 收入 > 0 且结余 > 0 | `进得比出得多 · 值得截图留证` | — |
| P8 | 兜底（无特殊模式） | `共 <N> 笔 · 钱包已阅` | `共 23 笔 · 钱包已阅` |

#### 周期变体（同模板按周期换词）

| 周期 | P3 变体 |
|---|---|
| `today` / `yesterday` | `今天<分类>说了算 · 占 <N>%` |
| `this_week` / `last_week` | `这周<分类>又赢了 · 吃掉 <N>%` |
| `this_month` / `last_month` | `这个月<分类>又赢了 · 吃掉 <N>%` |

#### 备选池（同条件多文案，避免反复分享看着一样）

每档配 2~3 条同义文案，用 `(period + 日期)` 做 seed 稳定选取 —— **同一天同一周期文案固定**（重复生成不跳字），跨天会变：

- P2 备选：`我基本上只是<分类>的搬运工` / `<分类>：这个家我说了算`
- P3 备选：`<分类>又赢了 · 吃掉 <N>%` / `<分类>一枝独秀 · 占 <N>%` / `<分类>遥遥领先 · <N>%`
- P5 备选：`收支逆差 · 请假装没看见` / `花超了 · 下期一定`
- P6 备选：`记了 <N> 笔 · 记账比赚钱勤快` / `<N> 笔 · 手比钱包快`
- P8 备选：`共 <N> 笔 · 钱包已阅` / `共 <N> 笔 · 收支两清` / `共 <N> 笔 · 存档完毕`

#### 实现约定
- 逻辑放 `receiptData.ts` 的 `pickPunchline(data, period): string`，**纯函数**，每档写单测。
- 分类名 > 4 字时，含分类名的模板降级到 P8 兜底，避免撑破单行。
- 文案库集中为模块内常量数组，便于 §9 的 A/B 整套换调性。

### 5.11 质感自检清单（验收用）

设计还原度按此逐项打勾，任一不满足则质感不成立：
- [ ] 纸张**非满宽**，能看到桌面留白与极轻投影
- [ ] 纸张**直角**无圆角
- [ ] 顶底齿**镂空**露桌面色，且底部齿有不规则抖动
- [ ] 全图**无彩色**，唯一彩色是二维码绿徽标
- [ ] 所有金额小数点**垂直对齐**（tnum）
- [ ] 有肉眼可辨但不喧哗的**纸纹噪点**
- [ ] 三种分割线（点/虚/实）层级可辨
- [ ] 支出金额是全图**唯一最大字**
- [ ] **无 emoji**
- [ ] 分类名超长时省略号，不换行不溢出版心

### 5.14 打印吐纸动画（Print & Tear）

#### 5.14.0 为什么这个动画不只是"锦上添花"

它同时解决了一个真实的架构隐患：**canvas 合成需要 100~300ms**（§6.6），这段等待原本只能用 loading 转圈填充 —— 而 loading 是"系统在忙"的负面信号。

**打印动画把这段等待变成了内容本身**：用户看到的不是"卡住了"，而是"小票正在被打印出来"。等待时间从**成本**变成了**仪式感**。这是**用叙事覆盖延迟**，比任何 loading 优化都有效。

> 设计准则：**动画时长 ≥ 合成时长**。若合成先完成，动画照常播完（不要为了"快"而截断，仪式感的价值高于 200ms）；若合成异常慢，动画在末帧停住等待，不空转。

#### 5.14.1 三段式动画

```
  ┌──────────────────┐
  │  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓  │  ← 打印机出纸口（固定不动，深色横条）
  └──────────────────┘
   ╱╲╱╲╱╲╱╲╱╲╱╲╱╲╱╲     ← ① 纸从口中吐出（向下位移 + 逐段显影）
  │  C O S T R A     │
  │  我 们 家 小 票    │
  │  ...             │     ② 内容随纸推出逐行显影
  │  支出  ￥2,350.00 │
  │  [码] 长按识别    │
   ╲╱╲╱╲╱╲╱╲╱╲╱╲╱      ← ③ 撕下：轻微回弹 + 齿边定型
```

| 段 | 时长 | 动作 | 缓动 |
|---|---|---|---|
| ① **吐纸** | 900ms | 纸张从出纸口向下 `translateY`：`-100%` → `0`，出纸口下方做 `overflow: hidden` 遮罩，制造"从机器里出来"的错觉 | `easeOut`（模拟步进马达先快后稳） |
| ② **显影** | 与①并行 | 内容**逐段**淡入（非整体）：抬头 → 元信息 → 清单逐行 → 合计 → 码区，每段间隔 60ms，`opacity 0→1` + `translateY 4rpx→0` | `easeOut` |
| ③ **撕下** | 260ms | 纸张整体轻微上弹 6rpx 再落回（`0 → -6rpx → 0`），同时底部齿边由直线"咔"地变为锯齿；伴随一次**轻微震动反馈** | `easeInOut` |

- **总时长 ≈ 1160ms**。这是精心权衡的结果：短于 800ms 没有仪式感，长于 1500ms 用户会烦（尤其反复切周期时）。

#### 5.14.2 关键细节（决定"像不像真打印机"）

| # | 细节 | 说明 |
|---|---|---|
| A1 | **出纸口必须存在且固定** | 纸从"虚空"滑出 = 普通入场动画；纸从一个**可见的出纸口**滑出 = 打印机。出纸口用深色横条（`rgba(28,27,26,0.88)`）+ 内侧一道高光，宽度略大于纸宽。 |
| A2 | **逐段显影而非整体淡入** | 热敏打印是**逐行成像**的。内容整体淡入会暴露"这是一张预先做好的图"；逐段显影才是"正在打印"。这是最关键的一条。 |
| A3 | **齿边在"撕下"瞬间才出现** | 吐纸阶段底部是**直边**（纸还连着机器），撕下瞬间才变锯齿。顺序错了动画就没有叙事逻辑。 |
| A4 | **震动反馈** | 撕下瞬间 `wx.vibrateShort({ type: 'light' })`。触觉是"撕纸"体感的一半，成本极低、收益极高。 |
| A5 | **步进感（可选增强）** | 吐纸位移叠加极轻微的阶梯抖动（每 ~80ms 一次 1rpx 顿挫），模拟步进马达。**慎用**：过度会像卡顿，建议 spike 后决定是否保留。 |
| A6 | **不加打印音效** | 微信小程序自动播放音频体验差（可能打断用户音乐、需授权），且分享场景常在安静环境。**不做音效**，用震动替代。 |

#### 5.14.3 触发时机（重要：不能每次都播）

| 场景 | 是否播放 | 理由 |
|---|---|---|
| 首次进入小票页 | ✅ 完整播放 | 建立"这是打印机"的心智，第一印象最关键 |
| 切换周期 chip | ❌ **不播**，仅内容 200ms 交叉淡入 | 反复播 1.2s 动画会烦躁；此时用户在"比较数据"，要快 |
| 点「重新生成/刷新」 | ✅ 播放 | 用户主动要求"再打一张" |
| 数据变更后自动刷新 | ❌ 不播 | 后台更新不应打断用户 |
| 点「发送给朋友」 | ❌ 不播 | 见 §5.14.4 |

> **核心判断**：动画是**首次的仪式**，不是**每次的开销**。这条决定了功能是"有惊喜"还是"有负担"。

#### 5.14.4 关于"发送时"是否加动画

**结论：不加。**

用户点「发送给朋友」时，意图是**尽快完成分享**，此时任何动画都是阻塞。而且 `wx.showShareImageMenu` 会立刻拉起系统面板，自定义动画会被系统 UI 覆盖，视觉上变成闪烁。

**替代方案**：把仪式感放在**生成时**（已有打印动画），发送时只做一次轻微的**按钮态反馈** + 直接拉起面板。

#### 5.14.5 实现方式（关键技术判断）

**动画不在 canvas 里做，而是在 WXSS 层做。**

理由：canvas 逐帧动画在小程序里性能差、代码复杂，且我们**已经有一张合成好的静态图**。正确做法是分层：

```
预览区结构：
  <出纸口>  (静态，深色横条)
  <遮罩容器 overflow:hidden>
     <image src={tempFilePath} />   ← 合成好的小票图，用 CSS transform 位移
     <显影遮罩层 × N段>              ← 覆盖在图上，逐段撤除实现"逐行显影"
  </遮罩容器>
```

- 位移与淡入全部用 **CSS animation / transition**（走 GPU 合成，60fps 稳定）。
- **逐段显影的取巧实现**：在小票图上覆盖若干与纸同色（`#faf8f2`）的横向遮罩块，按段依次 `opacity→0`，视觉上等同"内容逐段浮现"。比切图分段绘制简单得多，且不需要 canvas 参与。
- 段的 y 坐标**直接复用 §6.3 `measureReceipt` 输出的 layout**（各段绝对 y 已知），无需重复计算 —— 这是两段式布局设计的额外红利。
- 齿边变化：底部齿用一个独立的 `<view>` 承载（CSS `mask` 或预置齿形 png），撕下瞬间切换其显示。
- 遵守项目约定：动画时长走 `animation.duration`（150/250/350ms）与 `animation.easing` token 组合；本动画的 900ms 属自定义长时段，在实现处注明"打印动画专用、不进全局 token"。

#### 5.14.6 降级与可访问性

| 场景 | 处理 |
|---|---|
| 合成失败 | 不播动画，直接 toast 错误（不能播完动画才报错，那是欺骗） |
| 系统开启"减弱动态效果" | 通过 `wx.getSystemSetting` / `getSystemInfoSync` 判断，降级为 200ms 简单淡入 |
| 低端机掉帧 | 动画纯 CSS transform + opacity（无 layout 抖动），已是最优；若仍卡可关闭 A5 步进抖动 |
| 用户中途点击 | **允许打断**：点击预览区立即跳到动画末帧（不强制看完，尊重用户） |

## 6. 图片生成技术方案（小程序端）

调研结论：项目**无 canvas 生成图片先例**（趋势图刻意用 SVG 绕开）。本功能需**从零搭建 canvas 合成**。

### 6.1 技术选型
- 使用 **`wx.createOffscreenCanvas({ type: '2d' })`**（离屏 Canvas 2D）合成，避免同层原生 canvas 的滚动滞后问题（趋势图头注踩过的坑）。
- 合成完 `canvas.createImage` 贴二维码 → `wx.canvasToTempFilePath({ canvas })` 得临时文件路径。
- **像素比**：画布按 **固定 3x** 放大（750rpx → 2250px），不跟随设备 pixelRatio。理由：小票要保存/转发，需在任何设备上都清晰且**产出尺寸稳定可预期**；跟随 dpr 会导致低端机产出模糊图被转发。
- 金额格式化用 `utils/money.ts`（禁止 float）。

### 6.2 坐标系与 rpx 换算（关键工程约定）
- 设计稿全部以 **rpx** 标注（750 基准）。合成时统一：
  ```
  const SCALE = 3;                    // 固定 3x
  const px = (rpx) => rpx * SCALE;    // 750rpx -> 2250px
  ```
- **不要**用 `windowWidth/750` 做换算 —— 那是屏幕适配逻辑，会让不同机型产出不同尺寸的图。小票是**固定规格的图片产物**，与屏幕无关。
- 预览时再把这张固定尺寸的图按 `width: 100%` 缩放显示即可。

### 6.3 两段式布局：measure → paint
因高度自适应（分类行数可变），必须先算高再建画布：

**第一段 `measureReceipt(data) -> Layout`**（纯函数，可单测）
- 按 §5.4 的间距表累加各段高度：头部区 → 元信息区(3行) → 清单区(N行) → 合计区(2~3行) → 洞察区(2行) → 码区，得 `paperHeight`，再加上下齿高与桌面留白得 `canvasHeight`。
- 输出每个元素的绝对 `{ x, y }` 与样式引用，`paintReceipt` 只负责照着画。
- **好处**：布局逻辑与绘制解耦，可对"12 个分类""空数据""超长分类名"等 case 写纯单测，不依赖 canvas 环境。

**第二段 `paintReceipt(ctx, layout, images)`**
绘制顺序（严格自下而上，否则会覆盖）：
1. 桌面底色铺满
2. 纸张投影（`ctx.shadowColor/shadowBlur/shadowOffsetY` 后画纸形）
3. 纸张路径（含顶底齿形并入 path）填充 `#faf8f2`，**画完立即 `ctx.shadowColor='transparent'` 清除阴影**，否则后续文字全带阴影（canvas 常见坑）
4. 纸纹噪点（`clip` 到纸张路径内再撒点）
5. 各段文字与分割线
6. 二维码图片

### 6.4 三个必须提前解决的 canvas 实现要点

| # | 要点 | 做法 |
|---|---|---|
| C1 | **图片必须先 load 完再画** | `canvas.createImage()` + `await new Promise(r => { img.onload = r; img.onerror = r })`。二维码加载失败走 fail-open：跳过码区（但仍保留文案），不阻断出图。 |
| C2 | **等宽数字对齐** | 优先 `ctx.font = '500 84px "DIN Alternate", Menlo, monospace'`。若真机字族不可用导致宽度不一，**兜底方案：逐字符按固定步进绘制**（`measureText('0').width` 作为步进），保证小数点对齐。这是质感命门，需在 spike 中实测。 |
| C3 | **文本超长省略** | canvas 无原生 ellipsis。需自实现 `truncate(ctx, text, maxWidth)`：逐字 `measureText` 累加，超宽截断补 `…`。用于分类名与抬头账本名。 |
| C4 | **字距（letter-spacing）** | canvas 2D 无 `letterSpacing` 属性（部分环境有但兼容性差）。wordmark 与抬头需字距，**必须逐字符绘制**：累加 `measureText(char).width + spacing`。需配套算总宽以实现居中。 |

### 6.5 合成模块（新增）
`miniprogram/services/receiptComposer.ts`：
```
measureReceipt(data: ReceiptData): ReceiptLayout          // 纯函数，可单测
paintReceipt(ctx, layout, images): void                    // 纯绘制
composeReceiptImage(data: ReceiptData): Promise<{ tempFilePath, width, height }>
```
- 热敏纸专用色值（`#e8e6df` / `#faf8f2`）以模块内常量声明并注释"不进全局 token"（对齐项目"不跨组件复用"约定）。
- **纸纹噪点用固定 seed 的伪随机**，保证同一份数据两次生成的图一致（便于回归比对与问题复现）。

### 6.6 性能与体验
- 合成耗时预估 100~300ms（含图片 load）。交互上：切换周期先渲染**数据文本预览**，图片合成放在点击"保存/分享"时或 debounce 后台进行，避免每次切 chip 都卡一下。
- 生成期间按钮置 loading 态，防连点重复合成。
- 同一 `(period, dataSignature)` 的产出**做一次内存缓存**，重复分享不重复合成（signature 可用 totals+lines 摘要）。

### 6.7 页面归属与路由
- 新页放入 **`pages-stat/` 分包**（已配 `preloadRule` 预加载）：`pages-stat/receipt/index`。
- 入口：统计页（`pages/statistics/index`）新增「生成小票」按钮 → 导航到该分包页并透传 `familyId/ledgerId`。
- 落地页归因：分享/卡片携带 `?from=share&card=receipt&v=<tokens.version>`（对齐 README §3 埋点约定），落地回落 `pages/ledger/index`（与现有 share.ts 一致）。

## 7. 分享与保存链路

### 7.1 发送给朋友（图片消息，带码）
- `wx.showShareImageMenu({ path: tempFilePath })` 直接拉起「发送给朋友 / 保存图片」面板 —— 这是**图片消息**，好友收到的是图片，长按可识别图内小程序码。
- 埋点 `receipt.share`。

### 7.2 保存到相册
- `wx.saveImageToPhotosAlbum({ filePath })`；首次需 `scope.writePhotosAlbum` 授权，拒绝后引导去设置页。
- 埋点 `receipt.save`。

### 7.3 原生小程序卡片分享（点击直达，不带码，可选保留）
- 该页 `onShareAppMessage` 复用 `buildAppShareContent()` 的静态缩略图（遵守 safe-zone、无码），`path` 带 `?from=share&card=receipt`。
- 与 §7.1 并存：用户既能「发一张带码的图」，也能「发一张点击直达的小程序卡片」。
- **不实现 `onShareTimeline`**（对齐现有统计页决策：朋友圈落地页无法自定义 path）。

### 7.4 授权与失败兜底
- 相册授权被拒 → `wx.showModal` 引导 `wx.openSetting`。
- canvas 合成失败 → toast "小票生成失败，请重试"，不崩溃；保留静态兜底分享。
