# icon_key 跨端一致性 · 候选方案（讨论稿）

> ⚠️ **状态：候选方案，非定论。** 本文只记录讨论中提出的可选措施与评估，供后续决策参考，未拍板、未实施。
>
> 日期：2026-07-02 · 关联：`docs/design/category-icon-migration-plan.md`、`docs/design/category-icon-open-questions.md`

---

## 1. 背景

分类图标改用矢量字体后，图标以语义枚举 `icon_key`（如 `dining`/`breakfast`）在**服务端与客户端之间共享**：
- 服务端：分类配置里存 `icon_key`（seed / 自定义分类创建）；
- 客户端：`icon_key → 字形` 由内嵌字体（`iconfont.wxss` + `iconMap.ts`）渲染。

**特殊性**：`icon_key` 的"权威上界"在**客户端字体**——字体里没有的 key，客户端渲染不出来。

## 2. 不一致的场景分类

| 场景 | 危害 | 成因 |
|---|---|---|
| 服务端有、客户端**没有** | ⚠️ 渲染失败（tofu / 空白） | 见下两种 |
| ↳ **乱配/打错** | 填了字体全集里根本不存在的 key（笔误、拍脑袋） | 可控（写入端） |
| ↳ **版本领先** | key 合法（新字体有），但用户当前客户端版本字体还没更新到 | 半可控（发布节奏） |
| 客户端有、服务端没用 | ✅ 无害 | 图标没被用到而已 |

**结论**：只需防"服务端有、客户端没有"这一类，且分"乱配"与"版本领先"两种成因分别应对。

## 3. 候选措施（M1–M6）

### M1 · 客户端占位兜底
`resolveIconGlyph` 遇未知 key → 返回统一**占位图标**（不出 tofu、不难看）。
- 作用：任何不一致下客户端都不崩，是最终安全网。
- 现状：已有雏形（未知 → `other`），需去掉"单字原样返回"分支、并考虑专门的 `placeholder` 字形。

### M2 · 单一事实源（SSOT）
`icon_key` 全集只在 `scripts/icon-font/icon-registry.json` 定义；字体产物、`iconMap.ts`、服务端校验枚举**全部由它生成**，禁止手抄。
- 作用：根治"各处 key 集合定义漂移"，是 M3/M4/M5 的基础。
- 现状：`icon-registry.json` 已是 client 侧权威；`build-svg.mjs` 已有 `registry ↔ ICONS` 双向校验。缺"生成服务端枚举"这一步。

### M3 · 服务端写入校验
服务端写分类 icon（seed 配置 / `POST /categories`）时，校验 `icon_key ∈ SSOT 枚举集`，拒绝未知值。
- 作用：挡住"乱配/打错"——字体里没有的 key 根本入不了库。
- 现状：**当前完全不校验**（`createCategoryBodySchema.icon` 仅 `{type:string}`，原样入库）。

### M4 · OpenAPI enum
把 `Category.icon` / `CategoryCreate.icon` 从 `type: string` 升级为 `type: string, enum: [...]`（enum 由 SSOT 生成）。
- 作用：契约层锁定合法值，前后端代码生成 / 文档受益。
- 局限：仅契约/文档层，运行时拦截仍靠 M3。

### M5 · CI 一致性校验
一条 CI 断言：`registry ↔ iconMap ↔ 字体产物 ↔ 服务端枚举` 四处 key 集合一致，任一端漏同步即红。
- 作用：防长期多人协作演进中的跨端漂移。

### M6 · 发布顺序纪律（流程，非代码）
新增图标时：**先发含新字体的客户端 → 铺开 → 再在服务端启用新 key**。
- 作用：把"服务端领先客户端字体"的时间窗口降到最小。
- 现状：与分类图标迁移的发布顺序一致，已有先例。

## 4. 评估（复杂度 / ROI / 风险）

| 措施 | 复杂度 | 投入产出比 | 风险 / 局限 | 优先级 |
|---|---|---|---|---|
| **M1 客户端兜底** | 极低（改几行 + 可选占位字形） | ⭐⭐⭐⭐⭐ 唯一能防 tofu 花屏、兜底一切不一致 | 几乎无；不一致时图标降级为占位（可接受） | **必做（底线）** |
| **M6 发布顺序** | 零（纯流程） | ⭐⭐⭐⭐ 防"版本领先"窗口 | 依赖执行纪律 | **必做（流程）** |
| **M2 SSOT** | 低–中（已有 registry，加"生成 server 枚举"） | ⭐⭐⭐⭐ 根治定义漂移，其他措施的地基 | 低；需维护生成脚本 | **推荐** |
| **M3 服务端校验** | 中（seed + POST 校验 + 枚举来源） | ⭐⭐⭐⭐ 挡乱配、保 DB 干净 | 低；枚举未及时同步可能误拒新 key（靠 M2+M6 缓解） | **推荐** |
| **M4 OpenAPI enum** | 低（从 SSOT 生成 enum） | ⭐⭐⭐ 契约/文档锁定 | 低；enum 随版本增长需生成维护 | 可选 |
| **M5 CI 校验** | 低–中（一个 test 脚本） | ⭐⭐⭐ 防长期漂移，协作价值高 | 无 | 可选（长期推荐） |

## 5. 推荐方案（我的倾向）

**最推荐：M1 + M2 + M3 的组合（配合 M6 流程）。**

理由 —— **两端夹击、覆盖两类危险成因**：
- **写入端可控** → 用 **M2（SSOT）+ M3（服务端校验）** 从源头保证服务端**不产生**非法/未知 key（挡住"乱配/打错"）；
- **渲染端不可控**（老版本字体旧） → 用 **M1（客户端兜底）** 保证任何情况都不崩不花屏（应对"版本领先"）；
- **节奏** → 用 **M6（发布顺序）** 把"版本领先"窗口降到最小。

**分阶段建议**：
1. **第一步（几乎零成本、立即做）**：M1 客户端兜底 + M6 发布顺序纪律 —— 这是"防崩底线"，无论后续如何都应先具备；
2. **第二步（随 seed 单字→icon_key 替换一起做）**：M2 SSOT 生成 + M3 服务端校验 —— 替换 seed 时顺手把地基和校验建起来，避免以后加图标又埋隐患；
3. **第三步（有余力再加）**：M4 OpenAPI enum、M5 CI 校验 —— 长期协作的加固。

**为什么不是"全都做"**：M4/M5 是加固项，价值真实但非必需；在团队规模 / 迭代节奏不大时，M1+M2+M3+M6 已能覆盖绝大部分风险，ROI 最高。
