# 分类图标替换 · 待确认问题清单

> 用途：把「分类图标从汉字文本换成矢量图标字体」这项改动里，**需要产品 / 后端 / 数据同学确认**的问题集中列出，便于一次性对齐。
>
> 关联技术方案：`docs/design/category-icon-migration-plan.md`
>
> 状态：待确认（{{填写日期}}）

---

## 0. 背景（30 秒速览）

- 我们把小程序的分类图标，从「一个汉字」（餐/行/购…）换成了一套**线性矢量图标字体**（共 **81 个**图标）。
- 实现方式：给每个图标起一个英文语义名，我们叫 **`icon_key`**（如 餐饮=`dining`、加油=`fuel`）。分类只存这个名字，客户端拿到名字后用字体把图标画出来。
- 系统分类（我们预置的餐饮/交通/购物…）的图标已经全部改成了 `icon_key`。
- 上线要求「**先发新版小程序 → 用户更新铺开 → 再切服务端数据**」。在服务端数据切换前，**新版小程序会连着旧服务端**，此时旧服务端返回的还是「汉字」格式，导致图标显示异常（见下）。

### 已发现的过渡期问题（截图复现）
1. 一级分类显示成大号汉字（餐/行/购…），观感臃肿；
2. 二级分类显示成**父级的汉字**（早餐/午餐/晚餐 都显示「餐」），失去区分度。

### 拟采用的解决方案（方案 B）
新版客户端内置一张「**旧汉字 → icon_key**」对照表（如 餐→`dining`），把旧服务端返回的汉字也翻译成正确的矢量图标。这样过渡期一级分类能显示正确图标，观感统一。

**方案 B 是否成立、代价多大，取决于下面几个待确认问题。**

---

## 待确认问题

### Q1 · 【产品】自定义分类的「可选图标库」范围是多少？
- **问题**：用户创建自定义分类时，能挑选的图标，是**就用现在这套 81 个**，还是要提供一个**更大的图标库**（几百个任选）？
- **为什么问**：字体文件目前只装了这 81 个图标。如果用户能挑到第 82 个及以后的图标，字体里没有 → 画不出来（显示占位）。
- **影响**：
  - 若「就这 81 个」→ 现成的，字体无需改动，方案最干净；
  - 若「要更大的库」→ 需要把新增的那些图标也设计、做进字体（额外工作量），并纳入 `icon_key` 体系。
- **期望回答人**：产品 / 设计

### Q2 · 【产品 / 后端】自定义分类选定图标后，存储的是什么？
- **问题**：用户挑了某个图标，保存到数据库里的值，是图标的英文名 `icon_key`（如 `dining`），还是别的形态（数字编号 / 汉字 / 图片链接 / emoji）？
- **为什么问**：客户端认的是 `icon_key`。若存的就是 `icon_key`，客户端直接命中、正确显示；若是别的格式，需要额外翻译或兼容。
- **影响**：决定自定义分类能否复用同一套渲染逻辑、是否需要额外映射。
- **期望回答人**：后端 / 产品（若该能力尚在规划，请说明设计约定）
- **🔍 我方初步核查（代码层）**：
  - server 有创建接口 `POST /categories`（`CategoryCreate`，`icon` 必填 string），但**只校验"是字符串"，不校验取值、不加工，原样写入 icon 列**（`categoryRepo.insert` 直存）。
  - 也就是说，**存进去的是什么形态，完全由客户端传入决定**，服务端不强制是不是合法 `icon_key`。
  - **仍需你确认**：新版"选图标"功能**约定客户端传 `icon_key`**吗？（强烈建议如此——这样存进去就是合法 key，客户端直接命中，最干净。）

### Q3 · 【后端 / 数据】现网是否已有「用旧格式存图标」的自定义分类历史数据？
- **问题**：本次改动前，线上是否已经存在用户创建的自定义分类、且给它存了图标（旧格式）？
- **为什么问**：若存在这类旧数据，新客户端可能不认其图标格式，需要专门兼容。
- **影响**：若确认「没有」→ 方案更简单，无需为旧自定义数据兜底。
- **期望回答人**：后端 / 数据（DBA）
- **🔍 我方初步核查（代码层）**：
  - server **具备**创建自定义分类的能力（`POST /categories`，COSTRA-218）；
  - 但当前**小程序没有创建入口**（无分类管理页），且自定义分类的若干字段（`is_direct_default`/`is_parent_default`/`display_order`）都走默认值 —— 说明该功能的**前端入口尚未开放**；
  - 因此历史上的自定义分类数据，只可能来自**测试或直连 API 调用**，正常用户产生不了。
  - **仍需你核实**：生产库里是否真有自定义分类数据（SQL：`SELECT count(*) FROM categories WHERE family_id IS NOT NULL AND deleted_at IS NULL;`，如 >0 再看其 icon 取值）。

### Q4 · 【后端 / 数据】旧服务端「系统分类」的 icon 列，实际存过的汉字集合是否就是这 14 个？
- **问题**：请对生产库执行核查，确认系统分类历史上 icon 列存过的**去重汉字集合**。我方目前假设为这 14 个：
  `餐 / 行 / 购 / 活 / 旅 / 娱 / 转 / 他 / 薪 / 投 / 运 / 储 / 互 / 销`
  （建议 SQL：`SELECT DISTINCT icon FROM categories WHERE family_id IS NULL;`）
- **为什么问**：方案 B 的「汉字→icon_key」对照表必须覆盖这些汉字。若历史上用过表外的字（如早期版本改过），那些分类会掉占位。
- **影响**：决定对照表的完整性，是上线前必须完成的一次性核查。
- **期望回答人**：后端 / 数据（DBA）

### Q5 · 【产品 / 设计】过渡期「二级分类同组同图标」是否可接受？
- **问题**：在服务端数据切换前的过渡期，二级分类会显示**父级图标**（早餐/午餐/晚餐 都显示「餐饮」图标），失去细分区分度；等服务端切换数据后自动恢复为各自的细分图标。这个过渡期表现是否可接受？
- **为什么问**：这是方案 B 唯一残留的实质代价（旧服务端没有二级细分图标数据，客户端拿不到）。
- **影响**：若不可接受，需要额外方案（成本更高，且涉及被否决过的「按名称硬编码」思路）。
- **期望回答人**：产品 / 设计

### Q6 · 【产品 / 运营】发布顺序与过渡期知悉确认
- **问题**：确认并接受发布顺序——**先发新版小程序 → 等用户更新铺开 → 最后切服务端数据**。在这期间未更新到新版的老用户，分类图标会短暂显示异常（英文名/旧样式），直到其更新小程序。
- **为什么问**：这是「复用 icon 列改语义」方案的固有约束，需产品/运营知悉过渡期影响。
- **影响**：决定灰度/强制更新策略。
- **期望回答人**：产品 / 运营
