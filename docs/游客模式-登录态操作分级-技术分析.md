# 游客模式（免登录浏览）—— 登录态操作分级技术分析

> 状态：分析稿（待团队评审落地策略）
> 日期：2026-07-06
> 背景：应微信小程序审核要求，用户在**登录前**须能先体验小程序内容。
>       现有"登录页拦截、必须登录才能进入"的设计需调整，允许游客查看
>       明细 / 统计 / 协作 / 我的 四页并进行简单操作。
> 目标：厘清**哪些操作必须登录态**、**哪些可免登录**，并给出落地策略与登录触发点建议。

---

## 0. TL;DR

- **现状**：`app.ts` bootstrap 检测到未登录即 `wx.reLaunch('/pages/login/index')`；四个 Tab 页的 `onLoad/onShow` 也各自兜底 `hasValidSession()` → 未登录 reLaunch。整个 App 是"**先登录才有一切**"。
- **最硬的约束**：所有业务数据都以 `family_id`/`ledger_id` 为主键，而这两个 ID 是**登录时服务端下发**（`default_family_id`/`default_ledger_id`）。**未登录 = 没有账本上下文**，连"记一笔往哪记"都无从谈起。
- **各页数据来源天差地别**：
  - **明细页**账单列表读**本地 DB**（可离线）；
  - **统计页 / 协作页 100% 读服务端**（无任何本地计算路径），无 token + 无 familyId 直接 401；
  - **我的页**资料/宏观数据依赖 token 与服务端。
- **结论**：不能简单"去掉登录拦截"就完事。必须先选定**游客数据策略**（见 §5），再据此决定每个操作是"免登录直接可用 / 免登录降级只读 / 拦截并引导登录"。
- **推荐**：采用 **策略 B「本地游客账本」**——为游客本地预置一个 `guest` 账本 + 内置 fallback 分类，让游客能真正**记账、查看明细**（纯本地）；统计/协作/我的等**服务端强依赖操作**统一走"**引导登录**"。登录后把本地游客数据迁移上云。

## 1. 现有登录门控盘点（代码事实）

| 位置 | 行为 |
|---|---|
| `app.ts` bootstrap | `initAuth()` 后 `if (!isLoggedIn()) wx.reLaunch('/pages/login/index')` |
| `pages/login` onLoad | 已登录 → reLaunch 到 ledger；否则停在登录页等点击 |
| `pages/ledger` onLoad/onShow | `!hasValidSession()` → reLaunch login（onShow 是主防线，未登录不加载数据） |
| `pages/statistics` onLoad/onShow | 同上 |
| `pages/family` onLoad/onShow | 同上 |
| `pages/mine` onLoad/onShow | 同上 |
| `custom-tab-bar` attached | 未登录不揭示 tabbar（交由页面 reLaunch） |
| `services/request` 401 兜底 | 续签失败 → `clearToken()` + reLaunch login |

> 即：登录拦截是**多层冗余**的。改造游客模式要同时松绑这些点，而不是只改 `app.ts` 一处。

## 2. 数据来源分层（决定"能不能免登录"的根本）

| 能力 | 数据来源 | 是否需要 token | 是否需要 family_id/ledger_id |
|---|---|---|---|
| 明细账单列表 | **本地 DB**（`db.listMonthEntries`） | 否 | 需要 ledger_id 作为过滤键 |
| 记一笔 / 编辑 / 删除 | **本地 DB + outbox** | 写本地不需要；同步上行需要 | 需要 ledger_id 落库 |
| 记账分类树 | **服务端** `GET /categories`（按 familyId 预取）+ 内置 fallback | 拉新需要；fallback 不需要 | 需要 familyId |
| 明细页成员头像 / 成员资格校验 | **服务端** `getFamilyMembers`/`getFamilies` | 需要 | 需要 |
| 统计页（月度/年度/下钻） | **服务端** `statisticsApi.*` | 需要 | 需要 |
| 协作页（汇总/成员/分段/下钻） | **服务端** `familyApi.*` | 需要 | 需要 |
| 我的页 头像/昵称 | **token.raw.user** | 需要（本地 token） | 否 |
| 我的页 记账天数/笔数 | **服务端** `GET /users/me/overview` | 需要 | 否 |
| 增量同步 push/pull | **服务端** `/sync/*` | 需要 | 需要 family_id |
| 账本偏好持久化 | **服务端** `/users/me/preference` | 需要 | — |
| 公告红点/列表 | **服务端** `/announcements/*` | 需要 | — |

**核心洞察**：
1. **只有"明细列表 + 记账写本地"是真正可离线的**；统计页与协作页**没有任何本地计算能力**，是纯服务端读。
2. **分类是服务端资产**（虽有内置 fallback，可支撑游客离线选择分类）。
3. `family_id/ledger_id` 是登录时才有的服务端产物 —— 这是所有"游客数据"方案必须先解决的前提。

## 3. 逐操作分级：必须登录 vs 可免登录

分级口径：
- 🟢 **可免登录**（纯本地或纯前端交互，登录后无缝衔接）
- 🟡 **免登录降级**（可进入/浏览，但内容为空态/演示/引导，真实数据需登录）
- 🔴 **必须登录**（强服务端依赖，游客点击即引导登录）

### 3.1 明细页 `pages/ledger`

| 操作 | 分级 | 说明 |
|---|---|---|
| 进入页面、浏览布局 | 🟢 | 需松绑 onShow/onLoad 的 reLaunch |
| 查看本地账单列表 | 🟢 | `listMonthEntries` 读本地 DB；游客账本下有数据即可看 |
| 切月份浏览 | 🟢 | 纯本地索引 |
| 顶部账本切换 `<ledger-switcher>` | 🔴 | 多账本列表来自 `getFamilies`（服务端）；游客只有本地单账本，隐藏或禁用 |
| 成员筛选入口 / 成员头像 | 🔴 | `getFamilyMembers` 服务端；游客账本无成员维度，隐藏 |
| 成员资格校验 `_validateFamilyMembership` | 🔴 | 游客无 family，跳过 |
| 点条目进入编辑 | 🟢 | 走本地 `openEditMode`（见 §3.5） |

### 3.2 统计页 `pages/statistics`

| 操作 | 分级 | 说明 |
|---|---|---|
| 进入页面、浏览布局 | 🟡 | 可进入，但**无本地数据源** |
| 查看月度/年度报表 | 🔴 | `statisticsApi` 纯服务端，401；游客展示空态 + "登录后查看统计"引导 |
| 分类下钻 L2/L3 | 🔴 | 同上 |
| 成员维度横滑切换 | 🔴 | 依赖服务端成员数据 |
| 切月/年（scope 切换） | 🟡 | UI 交互可动，但拉数据会 401 → 引导登录 |

> ⚠️ 统计页是"游客可看性"最弱的一页：**它连一行本地计算都没有**。若产品要求游客能看到"自己刚记的账的统计"，需**新增本地统计计算**（较大工作量，见 §5 策略 B 附注）。

### 3.3 协作页 `pages/family`

| 操作 | 分级 | 说明 |
|---|---|---|
| 进入页面、浏览布局 | 🟡 | 可进入，展示"协作是什么"的介绍/空态 |
| 查看家庭列表 / 汇总 / 成员 / 分段 | 🔴 | `familyApi` 全服务端 |
| 创建协作账本 | 🔴 | `createFamily`（POST），协作本质是多人云端能力 |
| 生成邀请 / 撤销邀请 | 🔴 | `createInvite`/`revokeInvite` |
| 接受邀请 / 加入 | 🔴 | `acceptInvite`（invite-confirm 页已 `isLoggedIn` 兜底） |
| 移出成员 / 离开 / 解散 / 重命名 | 🔴 | 全服务端写操作 |

> 协作页天然是"登录后才有意义"的页。游客进入应看到**功能介绍 + 登录引导**，而非空白报错。

### 3.4 我的页 `pages/mine`

| 操作 | 分级 | 说明 |
|---|---|---|
| 进入页面、浏览布局 | 🟢 | 松绑 reLaunch |
| 头像 / 昵称展示 | 🟡 | 游客展示默认头像 + "点击登录"占位 |
| 记账天数 / 笔数（overview） | 🔴 | `GET /users/me/overview` 服务端；游客隐藏或显示本地统计 |
| 点头像进入完善资料 `profile-setup` | 🔴 | 画像走 `PATCH /users/me`；游客先登录 |
| 创建协作账本入口 | 🔴 | 同 §3.3 |
| 公告 + 红点 | 🔴 | `/announcements/*` 服务端 |
| 意见反馈 `open-type=feedback` | 🟢 | 微信原生能力，无需后端，可保留 |
| 关于 Costra / 隐私政策 | 🟢 | 静态页，免登录可看（合规上更应免登录可看） |
| 设置 | 🟢 | 当前仅 toast 占位 |
| 退出登录 | 🔴（不适用） | 游客态不显示"退出"，显示"登录"入口 |

### 3.5 记账面板 `components/expense-overlay`（跨页浮层）

| 操作 | 分级 | 说明 |
|---|---|---|
| 打开面板、计算器、切收支类型 | 🟢 | 纯前端 |
| 选择分类 | 🟢（降级） | 有内置 fallback 分类即可离线选；无 familyId 时 `loadCategoriesSync` 返回空 → **游客需喂 fallback** |
| 备注 / 日期选择 | 🟢 | 纯前端 |
| 费用性质 shared/personal | 🟡 | 仅多人账本有意义；游客单账本隐藏 |
| 账本归属切换 | 🔴 | `getFamilies` 服务端；游客只有本地单账本，隐藏 |
| **保存（写本地 + enqueue）** | 🟢 | `putEntry` + `outbox.enqueue` 纯本地；`created_by` 取 `getToken()?.user.id`，游客为 null（可接受） |
| 保存后的**同步上行** | 🔴（自动降级） | `pushDelta` 需 token，无 token 会 401 → 停在 outbox，登录后自动补推 |

## 4. 关键结论

1. **可真正免登录使用的核心闭环**只有一条：**记一笔（本地）→ 明细页查看（本地）→ 编辑/删除（本地）**。前提是给游客补齐两件东西：**一个本地账本上下文** + **内置 fallback 分类**。
2. **统计页、协作页、我的宏观数据、公告、偏好、同步** 都是强服务端依赖，游客**无法产出真实内容**，只能：进入页 + 空态/介绍 + 登录引导。
3. `family_id/ledger_id` 的"登录才有"是总闸门。要么给游客造一个**本地 guest 账本**，要么游客态下所有数据页都走空态。

## 5. 落地策略（二选一，建议 B）

### 策略 A：只读演示 / 空态浏览（改动小、体验弱）
- 游客可进入四页，但**任何真实数据都为空态**，任何写/读服务端操作点击即弹登录。
- 记账面板也可打开，但"保存"这一步就引导登录（不落本地）。
- 优点：改动最小、无数据迁移问题、审核可过。
- 缺点：游客几乎"看不到东西也做不了事"，体验接近"变相登录墙"，审核体验分低。

### 策略 B：本地游客账本（推荐，改动中等、体验完整）
核心：**未登录时也提供一个纯本地的 `guest` 账本上下文**，让"记账→明细"闭环真正可用。

需要落地的关键点：
1. **游客账本上下文**：`initAuth` 无 token 时，不再 reLaunch，而是写入一个本地 `FamilyContext`（如 `family_id='__guest__'`, `ledger_id='__guest_ledger__'`, `family_kind='personal'`, `ledger_name='我的账本'`），不落服务端偏好。
2. **内置 fallback 分类**：`categoryService` 已有内置 fallback（§categoryService.ts L78）。游客态让 `loadCategoriesSync('__guest__')` 直接命中 fallback，记账面板分类不为空。
3. **松绑各页 reLaunch**：四页 onShow/onLoad 的 `!hasValidSession() → reLaunch` 改为"游客态放行 + 相应降级"（隐藏成员/切账本/统计拉取等 🔴 操作）。
4. **登录触发收敛到一处**：提供统一 `requireLogin(reason)` 门面（弹登录引导或跳登录页），所有 🔴 操作点击时调用。
5. **同步自动隔离**：`syncScheduler`/`pushDelta` 在游客态下不触发（无 token 必 401）；outbox 数据保留。
6. **登录后数据迁移**：游客点登录成功后，把本地 `__guest_ledger__` 的 entries 迁移/改绑到服务端下发的 `default_ledger_id`，重写 outbox 的 ledger_id 后再触发首次 sync。**这是策略 B 唯一有技术风险的点，需单独设计**（改键、去重、幂等）。

> 附注（统计页游客可看性）：若产品坚持游客也要看到统计，需为统计页新增**本地计算路径**（用本地 entries 现算月度/年度聚合），这是策略 B 之外的**额外较大工作量**；否则统计页游客态维持空态 + 登录引导即可。

## 6. 登录触发点建议（策略 B 下）

游客态下，以下操作点击时统一触发"引导登录"（弹层说明收益，而非直接踢到登录页打断）：

- 统计页：查看报表 / 任何下钻 / 成员维度
- 协作页：创建协作 / 邀请 / 加入 / 任何成员与家庭写操作
- 明细页：切换账本、成员筛选
- 我的页：完善资料、记账天数笔数、公告、创建协作
- 记账面板：账本归属切换（多账本）
- 任意需要"跨设备/多人/云端持久化"的动作

免登录始终可用：记一笔（本地）、看本地明细、编辑/删除本地账单、计算器、备注、意见反馈、关于/隐私静态页。

## 7. 待团队确认的问题

1. **策略 A 还是 B？** 建议 B（体验完整、审核友好），但需接受"游客数据迁移"这一块设计成本。
2. **统计页游客态**：接受"空态 + 登录引导"，还是投入做**本地统计计算**让游客也能看？
3. **登录引导形态**：统一弹层（软引导，可关）还是跳登录页（硬打断）？建议软引导。
4. **游客数据保留边界**：游客卸载/清缓存即丢失，是否需要在登录引导里明确告知"登录后云端永久保存"？
5. **`created_by=null` 的游客 entry**：迁移上云时按登录用户回填，是否需要在 UI 层对游客 entry 的成员维度做屏蔽？（游客本就单账本无成员维度，风险低。）
